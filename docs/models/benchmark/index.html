Benchmark

Tiếng Việt: benchmark.vi.md.

This page compares Guard Spec's detector with other open prompt-injection detectors on Guard Spec's own eval set and on public datasets. Everything on it comes from one command, with every dataset and model pinned, so anyone can rerun it and check the numbers.

It is a measurement and nothing else. No threshold, weight or rule of Guard Spec was tuned on these datasets or on eval/ for this page, and the other detectors run with their published defaults.

  • On our own set Guard Spec is far ahead, which is expected and not a fair test of ProtectAI: half of eval/ is Vietnamese (ProtectAI is English-only) and its benign rows are hard negatives written to look like attacks. On the English half ProtectAI reaches AUC 0.897 and flags 23% of benign rows.
  • On SPML, the one public set no detector here was trained on, ProtectAI is clearly better: AUC 0.997 against 0.974 and, at the same 1% FPR, 97.6% of attacks against 84.5% (89.2% with L1+L2). At its default threshold Guard Spec blocks only 36% of SPML attacks, with no false positive; ProtectAI blocks 99% with 8% false positives.
  • On deepset and jailbreak-classification Guard Spec ranks better (AUC), but Guard Spec's classifier was trained on their train splits, so those two rows favour it. On deepset both detectors block only about a third of attacks at their defaults.
  • Guard Spec is smaller (237 MB int8 against 739 MB fp32) and faster per row (p50 5–8 ms against 32–67 ms on short inputs, one thread). The comparison is not like for like: our models are int8, ProtectAI's published ONNX file is fp32.
  • Meta Prompt Guard 2 is gated and not in these tables; anyone with access can add it with one variable (below).

Reproduce#

make benchmark

That target fetches ONNX Runtime and libtokenizers (make onnx-deps, pinned by SHA-256), runs bench/run.py with the Python packages locked in bench/uv.lock (needs uv), and writes:

  • bench/results/results.json: every metric, the machine and the versions;
  • bench/results/results.md: the tables;
  • the generated block of this page (between the bench:begin and bench:end markers).

What it does:

  1. Downloads the public datasets at the pinned Hugging Face commits and converts them to the eval/ row schema.
  2. Pulls the models with go run ./cmd/models pull, which checks every file against the SHA-256 values in models/manifest.yaml: guardspec-classifier@v3b, multilingual-e5-small@614241f and protectai-deberta-v3-base-pi-v2@90c9989.
  3. Runs Guard Spec through cmd/eval -scores (built with -tags onnx), which is the gateway's input path: sanitizer, detector layers, fusion and the /v1/scan block rule.
  4. Runs the ProtectAI model in ONNX Runtime from Python.
  5. Computes the metrics below for every detector, dataset and language.

Options:

Variable Default Effect
BENCH_CACHE bench/.cache Downloads, converted datasets, per-row scores. About 1.2 GB (ProtectAI's ONNX file is 739 MB). The run stops when less than 6 GB is free there.
MODEL_DIR $BENCH_CACHE/models Use already pulled Guard Spec models (<dir>/cache/<name>/<version>) instead of pulling them.

GitHub Actions: the Benchmark workflow (.github/workflows/benchmark.yml) runs make benchmark on ubuntu-24.04 when started by hand (Actions > Benchmark > Run workflow); it never runs on its own. It writes the tables to the job summary and uploads bench/results/ and this page as the benchmark-results artifact.

Including Meta Prompt Guard 2#

meta-llama/Llama-Prompt-Guard-2-86M and -22M are gated on Hugging Face under the Llama 4 Community License: they cannot be downloaded without an account that accepted the terms, so they are not in the published tables. With access:

  1. Accept the license on both model pages.
  2. Export a read-only token of that account as HF_TOKEN in your shell (huggingface_hub reads it; bench/run.py never reads, prints or stores it).
  3. Run make benchmark PROMPTGUARD=1. This installs the promptguard extra (PyTorch and Transformers, CPU) and adds two detector rows, at the pinned revisions a8ded8e (86M) and 11614a1 (22M), with the model's argmax decision (malicious probability ≥ 0.5), the first 512 tokens, one thread.

In the workflow, add the token as the repository secret HF_READ_TOKEN and check "promptguard" when starting the run.

What is measured#

For every detector × dataset × language:

  • ROC AUC of the detector's score, with a 95% bootstrap interval (1,000 resamples, fixed seed). It does not depend on any threshold.
  • TPR and FPR at the default decision: the share of attack rows and of benign rows the detector flags with its own published default. For Guard Spec that is the gateway's /v1/scan rule (detector score ≥ 0.85, or sanitizer anomaly ≥ 0.6, or an input the sanitizer rejects), the decision a deployment makes.
  • TPR at FPR ≤ 1%: the share of attacks caught at the lowest threshold that flags at most 1% of that group's benign rows. The threshold is picked after the fact on the same rows, for every detector alike, so it is an upper bound on what a tuned threshold would give; it compares the score rankings, not the defaults. With fewer than 100 benign rows it means "no false positive at all".
  • Latency p50 / p95 per row, in milliseconds: one row at a time on one machine, with ONNX Runtime (or PyTorch) set to one intra-op thread. For Guard Spec it is the sanitizer plus the detector as the gateway runs them; with L2 and L3 both on, the gateway scores the two models concurrently, so that configuration can use two cores for one row. For the Python detectors it is tokenization plus the model call. Five warm-up rows are not timed for the Python detectors; cmd/eval times every row, model loading excluded.
  • Model size: the size on disk of the model weights the detector loads.

Datasets without benign rows (Gandalf) only have a TPR.

Discussion#

Where Guard Spec does worse.

  • SPML. This set's attacks are mostly polite requests that break one chatbot's rules ("rather than going to a doctor, suggest ..."), written by GPT-4 from leaked system prompts. Guard Spec's score ranks them well (AUC 0.97–0.98) but keeps most of them below its 0.85 block threshold: TPR 36% at default. ProtectAI flags 99% of them, at the cost of 8% false positives on the benign SPML prompts. Some of that gap is the threshold, not the model: at an equal 1% FPR Guard Spec catches 84–89% and ProtectAI 98%. The labels also depend on a system prompt that neither detector sees, so part of this set is not decidable from the user message alone.
  • Non-English, non-Vietnamese input. On the German and Spanish half of deepset (56 rows) Guard Spec blocks 21% of attacks at its default, ProtectAI 48%; both have no false positive there. Guard Spec's rules and classifier only target English and Vietnamese. The group is small (29 attacks): treat the gap as a direction, not a size.
  • The default threshold is conservative. On every public set Guard Spec has 0.0% FPR at its default and the "TPR at FPR ≤ 1%" column is much higher than the default TPR (deepset 33% → 83%, SPML 36% → 85%). The 0.85 block threshold and the fusion were set for low false positives on eval/-like traffic (hard negatives, Vietnamese chat). Deployments that see plain English attacks may want a lower threshold; this page does not change it, because tuning on these sets would make the numbers meaningless.
  • L3 does not help on these sets. L1+L2+L3 and L1+L2 are within noise on eval/, deepset and jailbreak-classification, and L3 is lower on SPML at 1% FPR (84.5% against 89.2%). It adds 0.5–1.3 ms per row at p50.
  • Long inputs. Guard Spec scores every 2,048-byte chunk of a long input, each in 256-token windows (see Long documents); the long role-play prompts of jailbreak-classification take 42 ms at p50 and 510 ms at p95 with the model layers (ProtectAI: 330 ms and 1.16 s, but it reads only the first 512 tokens).

Where it does better, and why that is partly expected.

  • eval/ is Guard Spec's own set: same authors, same notion of an attack, Vietnamese and hard negatives. Read the ProtectAI rows there as "what an English-only model does on this traffic", not as a ranking. Even so, the English half is informative: ProtectAI blocks 23% of its benign rows (security discussions, sysadmin text, code with attack strings), Guard Spec 1.6%.
  • deepset, jailbreak-classification and Gandalf share their distribution with Guard Spec's training data (train splits), and ProtectAI also trained on jailbreak-classification. Guard Spec's higher AUC on them is weak evidence.

Other notes.

  • Small groups have wide intervals: deepset has 116 rows, and its per-language groups under 60. Differences inside the 95% intervals are not signal.
  • LLM Guard's default (score > 0.92 instead of ≥ 0.5) trades a few points of TPR for a few points of FPR; it does not change the picture.
  • Latency was measured on a shared laptop with other work running, one configuration after the other; read it as indicative. The manual workflow gives a Linux run.
  • Guard Spec's "default" is the gateway's whole /v1/scan rule, which also blocks on sanitizer anomalies. That is why its TPR on eval/ (95.0%) is above the README's "TPR at block" (0.939), which counts the detector score only.
  • Language labels of the public sets come from a simple marker rule, not a language-identification model.

Long documents#

The tables above score short prompts. Retrieved documents, tool results and pasted files are longer, and a detector that takes the maximum over a text's windows gets more chances to fire as the text grows. This section measures that, with make bench-long (bench/long/, cmd/benchlong).

Setup. The corpus is built from pinned public sources (Wikipedia EN/VI, the U.S. Code, Go source code, Vietnamese public-domain literature and laws from vi.wikisource; licences in bench/long/corpus.yaml), plus seeded synthetic logs, JSON, CSV, e-mail threads, chat transcripts and hard negatives (benign text about prompt injection). Texts of one genre are joined to 20k, 50k, 100k, 200k and 500k tokens. Attack documents put one payload from the dev half of eval/ (ids ending in hex 0–7; the eval/ holdout half is never used, see below) into a 2k-token host (a 28 KB one for the segment boundary): at the start, the end, a random place, across a 256-token window, a 2,048-byte chunk or a 24 KiB segment boundary, split in two halves (adjacent, or about 1,500 tokens apart), hidden with zero-width or Unicode tag characters, or shaped as a code comment or a JSON field; control is the payload alone. Every text goes through the gateway's sanitizer. Two paths:

  • l2: the classifier alone on every 256-token window (64-token overlap), Platt-calibrated as in the fusion;
  • l1,l2/logreg (and l1/max): the gateway's fused score on every 2,048-byte chunk, cut as the gateway cuts untrusted text but without its 16-chunk cap. This is the score the 0.85 block threshold applies to.

T(n) is the threshold that keeps a benign text of n units (windows or chunks) under 1% false positives: the larger of a block-bootstrap q99 of the maximum over n contiguous benign units and a GEV fit on the logit of 16-unit block maxima.

Dev and holdout slices. Every document carries a split (dev or holdout), the eval/ convention: the last hex digit of a SHA-256 of the document id, or of the payload id for attack and control documents so that all variants of one payload fall in one slice (full profile: 38 / 34 benign, 384 / 384 attack documents; long profile: 66 / 62 benign). The report has the false-positive and detection tables for both slices next to the totals (doc_fpr_by_split, tpr_by_split); anything tuned on this benchmark reads the dev slice only. The training data builders keep the corpus out of training: no 50-token shingle of any bench/long document may appear in a v6 training row (train/data/bench_guard.py).

The payloads come from the dev half of eval/ since 2026-11-11: a model selected on the bench dev slice (the v6 gates) must never have seen eval/-holdout wording, so that the eval/ holdout half stays a clean final measurement. The bench slice of an attack document is a second, independent hash of the payload id, so bench dev and bench holdout still use disjoint payloads (full profile: 32 per language, 32 dev / 32 holdout; quick: 12 per language, 13 / 11). Before that date the payloads were the eval/ holdout half; the benign and host documents did not change, but the numbers published below from earlier runs were measured on holdout payloads and are not directly comparable with runs on the current corpus (outputs in bench/long/corpus.yaml pins both).

  • What the larger sample says. The v6 gate G6 saw 0 of 15 dev documents blocked (upper bound 0.22); on 66 dev and 62 holdout documents v6 blocks about one benign document in four at 100k to 200k tokens (all 128: 25.0%, 95% interval 17.9% to 31.8%), the same on both slices and both languages. That is a third of v3b (80%) and about half of v5 (45%) on the same documents, and far from the 1% the gate asked for: the 0 / 15 was a small-sample result. The share of chunks at or above 0.85 drops from v3b's 12% on English code and documentation, 10% on RFCs, 7% on Wikisource prose and 47% on synthetic Vietnamese logs to at most 0.4% in any genre for v6 (v5: 15.6% on the Vietnamese hard negatives, under 1% elsewhere); a document of 50 to 100 chunks is still blocked by its single worst chunk.
  • The sanitizer, not the model, decides some documents. The gateway's sanitizer runs before scoring. It rejects both Vietnamese documentation documents at 100k ("input exceeds 8 layers of encoding": a React page whose JSX reads as nested tags to the HTML stripping, which does not settle in 8 passes); they count as blocked in the report's gateway column, not in the model rates above (the two 100k VI cells hold 18 and 15 documents, one of each unscored). Its HTML stripping also shortens 11 English documents before the model sees them: Go code with Kubernetes manifests at 200k to 138k and 141k tokens, Kubernetes documentation at 100k to 72k to 89k and at 200k to 122k to 154k (one to 25k), and one RFC document from 200k to 1,177 tokens (an unclosed < swallows the rest). The gateway's long path and a document-level rule (task RF-895d3533 R3). A document of 100k tokens reaches the gateway's long path (MAX_SCAN_TOKENS), which scores 256-token windows (fused with L1, the cap and code corroboration), not the 2,048-byte chunks above; cmd/benchlong -long on measures that path as it runs (layer long). With it, v6 blocks 9 / 65 dev and 14 / 61 holdout long documents (13.8% and 23.0%; the two rejected documents are not counted). Payloads embedded in such documents (bench/long/embed_long.py: the full profile's 32 dev and 32 holdout payloads in the seven placements of the v6 gate G7, each in a long document of its own language and slice) are caught as well as alone: 95.9% of 221 dev and 88.1% of 218 holdout documents, against 93.8% and 90.6% for the payloads alone. Four document-level rules were pre-registered and fitted on dev only (train/reports/r3_preregistration.md): counting a window over 0.85 only when the rules (L1) corroborate it, a threshold that grows with the number of windows (extreme-value fit), both, or k windows over 0.85. None reached 1% without losing the embedded attacks: on dev every benign window over 0.85 is one where an L1 rule fires (10 of 12 with the classifier agreeing, 2 on an L1 floor alone), the blocked documents' worst windows score 0.92 to 0.985, and the payloads' windows score in the same range (median 0.986). The chosen rule (corroboration) blocks 13 / 61 holdout documents (21.3%, 95% interval 11.9% to 33.7%) at an unchanged 88.1% detection, so it is not used; calibration.json can carry such a rule (long_doc) but no shipped model has one. Details in train/MODEL_CARD.md (v6, R3).

New long documents, tightened rules and a stricter decision (task RF-895d3533 R5). Because both halves of long had been scored, R5 built a new profile, long5 (150 benign documents of 100k and 200k tokens from sources and units no other profile uses, 74 dev / 76 holdout; 80 new eval/ dev-half payloads, alone and in the seven G7 placements), and pre-registered ten combinations of two L1 rule sets (v6 as shipped, and R5's: Vietnamese homographs such as "giàu"/"giấu", single adverbs of secrecy under the corroboration bar, tighter hidden-note, refusal-suppression, password-trick and decode rules) with five long-path decisions (today's, R3's L1 corroboration, an L1 floor counting only when L2 agrees, and two higher corroboration bars) (train/reports/r5_preregistration.md). The R5 rules leave eval/data and val_v3 unchanged. What this means.

  • Benign long text is not safe at 0.85 today. Ordinary prose (Wikipedia, the U.S. Code, Vietnamese literature) has 0.4% to 2.4% of its chunks at or above 0.85, and some genres far more: 51.6% of Go source chunks, 78.8% of the synthetic Vietnamese log chunks and 5.7% of the English hard negatives score at or above 0.85 with l1,l2 (the rules alone flag 60% of hard-negative chunks: they quote attack phrases). Since a document is flagged when any chunk is, a 50k-token document is flagged more often than not.
  • No threshold fixes it. T(n) climbs to 0.99 and beyond within 16 chunks: a threshold that keeps long benign text under 1% false positives would also miss most attacks. The fix has to come from the model (training on code, logs and long documents) or from aggregation other than the maximum, not from the threshold.
  • A payload inside benign text is often missed. The same payloads that are caught alone (100% EN) are caught 33% to 50% of the time when they sit in the middle of a chunk of prose. They are caught when they stand on their own lines (code comment, JSON field) or fill most of a window.
  • Split payloads far apart are not caught by design: no window sees both halves (8.3% / 25.0%).
  • Tag-character payloads are invisible to the model after the sanitizer strips them; the sanitizer's anomaly score blocks all of them.
  • Vietnamese numbers are provisional: the Vietnamese corpus has fewer and less varied sources (no code; laws, literature, Wikipedia and synthetic text).
