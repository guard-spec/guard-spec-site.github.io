Sizing and layers

Tiếng Việt: sizing.vi.md.

How much CPU, memory and disk Guard Spec needs, by detection layer. The gateway dominates: its memory is set by which models it loads, and its CPU by how many prompts per second the model layers score. The control plane and Postgres are small next to it.

Choosing layers#

DETECTOR_LAYERS picks the layers (one variable, in .env):

Mode DETECTOR_LAYERS Models pulled Use it when
Full (default) l1,l2,l3 classifier + e5 embedder, about 270 MB Production with RAM to spare; L3 matches org-specific exemplars and adds recall on paraphrased attacks
Light l1,l2 classifier only, about 135 MB A laptop, a small VM, a personal setup; about half the memory and 2 to 3 times the throughput of full
Rules only l1 none Very small hosts, or when false positives cost more than missed attacks; much weaker on paraphrases 
# quick start in light mode (writes DETECTOR_LAYERS=l1,l2 into the new .env)
DETECTOR_LAYERS=l1,l2 scripts/quickstart.sh
# an existing stack: set DETECTOR_LAYERS=l1,l2 in .env, then
docker compose -f docker-compose.yml up -d

models-init pulls only what the layers need, and /readyz shows the active layers ("layers":["l1","l2"]). What each layer detects and how they are fused: README, Models and Benchmarks.

Measured resource use#

Source. Measured on 2026-11-06 by the maintainers on one machine: an Apple M3 Max (arm64) MacBook Pro, Docker Desktop 28.4 with a Linux VM of 14 vCPUs and 15.4 GiB, images ghcr.io/guard-spec/guard-spec-gateway:0.1.0 (linux/arm64) and -control-plane:0.1.0, models guardspec-classifier@v3b and multilingual-e5-small@614241f. Memory and CPU are docker stats (sampled about once a second during the run; CPU 100% = one core). Load is ApacheBench, 8 concurrent clients, POST /v1/chat/completions with a system message and a 350-character user prompt, the stub upstream (no UPSTREAM_LLM_URL), so the numbers are the guard's own cost; every request also writes an audit row. Other hardware, x86-64 CPUs in particular, will differ: measure on yours (below) before you size a fleet.

Recommendations#

Starting points, from the tables above plus headroom. Only the "small team" row matches a measured configuration; the others are extrapolated from it. Requests/s are the guard alone; your upstream LLM's latency comes on top and does not use the gateway's CPU while it waits.

Setup Layers Host Gateway limit Roughly handles
Personal / laptop l1,l2 2 vCPU, 2 GB RAM free none tens of requests/s
Small team, one VM l1,l2 2 vCPU, 4 GB 2 CPUs, 1 GiB about 100 requests/s
Startup production, one VM l1,l2,l3 4 vCPU, 8 GB 2 to 3 CPUs, 2 GiB about 50 to 80 requests/s
More traffic l1,l2,l3 several gateway replicas (Kubernetes, Helm chart) 2 CPUs, 2 GiB each add replicas; throughput scales with cores
  • Memory: give the gateway at least 1.5 x its measured peak (light 768 MiB, full 1.5 GiB); the model weights are loaded once per process, whatever the concurrency.
  • CPU: throughput grows with cores up to INFERENCE_MAX_CONCURRENCY x INFERENCE_INTRA_OP_THREADS; set their product to the CPUs the gateway may use. More than that only adds contention.
  • DETECTOR_CASCADE=true skips L2 and L3 when L1 alone is decisive, which saves CPU on obvious traffic; it changes scores, so check it against your traffic first.
  • Rate limits (RATE_LIMIT_RPM) and an upstream timeout keep a burst from queueing up behind the model layers.
  • Kubernetes: the Helm chart's gateway defaults (500m CPU / 1Gi request, 2Gi memory limit) fit the full detector's measured peak; set INFERENCE_MAX_CONCURRENCY and INFERENCE_INTRA_OP_THREADS to the CPU limit as above (gateway.env), and scale with gateway.autoscaling (HPA). See values.yaml, the per-cloud examples in deploy/helm/guard-spec/examples/ and README, Kubernetes.

Long inputs#

A long text costs CPU in proportion to its length: the gateway cuts it into 2,048-byte chunks (untrusted text first into 24 KiB segments) and the classifier scores each chunk in 256-token windows. Today one request carries at most 128 KiB of untrusted text (about 30k tokens) and a single message at most 16 chunks; the numbers below say what larger documents would cost. How well the detector does on long text (false positives grow with length) is in benchmark, Long documents.

Measured with make bench-long (cmd/benchlong, the l1,l2 detector, one document at a time, K chunks of a document scored in parallel; 20k-token Wikipedia documents in English and Vietnamese). intra is INFERENCE_INTRA_OP_THREADS; "ORT default" lets ONNX Runtime use every core for each run.

2 vCPU (AMD EPYC 9V74) GitHub ubuntu-24.04 runner, taskset -c 0,1, quick profile, 2026-11-09 60.3 2,879 (K = 2) 4,571 (K = 2) about 50,000 0.41 (intra 1), 0.79 (default) 3.7 to 4.2 s

16 vCPU (x86) estimated about 12,000 about 120,000 about 1.5 s
GPU not measured (task RF-b74de2b9)
  • The two runner rows are measured, but on different CPUs (GitHub assigns the host): the 2 vCPU job got a newer EPYC 9V74, the 4 vCPU job an EPYC 7763 that also ran the full corpus, so the 2 vCPU row is faster. Shared cloud vCPUs vary by 1.5 to 2 times between runs; read them as a range.
  • x86 cloud vCPUs are 3 to 4 times slower per core than an M3 Max here (about 780 tokens/s per vCPU at intra 1, K = 4, on the 4 vCPU runner against about 2,300 per M3 Max core).
  • The 8 and 16 vCPU rows are estimates, not measurements: they scale the 4 vCPU runner's rate per vCPU linearly, which assumes K and INFERENCE_MAX_CONCURRENCY grow with the cores. Replace them with your own run.
  • For a 10 s scanning budget this means roughly 30k to 50k tokens per request on 2 to 4 vCPU, 60k on 8 and 120k on 16 (estimated); 200k tokens in 10 s needs about 32 dedicated vCPUs or a GPU (not measured yet).
  • CPU per token barely changes with K or intra: more parallelism cuts the wall time of one document, not its cost. A server scanning documents for several users at once gets the same total throughput from intra 1 and many concurrent runs as from fewer, wider runs.
  • The full per-run tables (L2 alone, every K, wall time per document) are in bench/results/long-m3max-local.md, long-gh-ubuntu-24.04-4vcpu.md and long-gh-ubuntu-24.04-2vcpu.md. The runner runs predate the 0.4.2 code/log fixes, so their false-positive tables show the 0.4.1 detector; latency is unaffected.

Measure long inputs on your hardware#

make bench-long                    # PROFILE=quick: about 1.6M tokens, about 7 minutes on an M3 Max
make bench-long PROFILE=full       # about 9.5M tokens
# your own documents, no Python needed: one .txt file per document
go run -tags onnx ./cmd/benchlong -docs ./my-docs -lang en -host my-server

make bench-long needs uv for the corpus builder and downloads its pinned public sources once into bench/.cache. Both write bench/results/long-<host>.json and .md; the -docs form reports the score distribution, false positives and latency of your texts (it has no attacks, so no detection rate). Pin cores with taskset -c 0,1 and set INFERENCE_MAX_CONCURRENCY to match, as the 2 vCPU row does.

Disk#

  • Models: about 135 MB (light) or 270 MB (full) per version kept, plus older versions you pulled for rollback.
  • Images (unpacked, arm64): gateway 285 MB, control plane 46 MB, Postgres 415 MB, Caddy 88 MB.
  • Postgres: the audit table grows with every request. Measured on the stack above: 20,020 rows took 7.4 MB with indexes, about 380 bytes per request with the default AUDIT_STORE_CONTENT=false (hashes and lengths only). 1 million requests a day kept for the default 90 days (AUDIT_RETENTION_DAYS) is about 34 GB. Storing content adds the size of every prompt and response.
  • Logs: the production compose keeps at most 50 MB per container.

Measure on your hardware#

# 1. a key (see the README quick start), then a body like your traffic
cat > body.json <<'EOF'
{"model":"m","messages":[{"role":"user","content":"<a prompt of typical length>"}]}
EOF
# 2. load, while watching the containers
ab -n 5000 -c 8 -p body.json -T application/json -H "x-api-key: $KEY" \
  http://localhost:8080/v1/chat/completions
docker stats    # in another terminal
# 3. audit table size per row
docker compose exec postgres psql -U ps -d guardspec -c \
  "SELECT count(*), pg_size_pretty(pg_total_relation_size('requests')) FROM requests"

Run it without UPSTREAM_LLM_URL (stub answers) to see the guard alone, and once per DETECTOR_LAYERS value you consider. Reports with other hardware are welcome in an issue.
