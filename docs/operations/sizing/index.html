Sizing and layers

Tiếng Việt: sizing.vi.md.

How much CPU, memory and disk Guard Spec needs, by detection layer. The gateway dominates: its memory is set by which models it loads, and its CPU by how many prompts per second the model layers score. The control plane and Postgres are small next to it.

Choosing layers#

DETECTOR_LAYERS picks the layers (one variable, in .env):

Mode DETECTOR_LAYERS Models pulled Use it when
Full (default) l1,l2,l3 classifier + e5 embedder, about 270 MB Production with RAM to spare; L3 matches org-specific exemplars and adds recall on paraphrased attacks
Light l1,l2 classifier only, about 135 MB A laptop, a small VM, a personal setup; about half the memory and 2 to 3 times the throughput of full
Rules only l1 none Very small hosts, or when false positives cost more than missed attacks; much weaker on paraphrases 
# quick start in light mode (writes DETECTOR_LAYERS=l1,l2 into the new .env)
DETECTOR_LAYERS=l1,l2 scripts/quickstart.sh
# an existing stack: set DETECTOR_LAYERS=l1,l2 in .env, then
docker compose -f docker-compose.yml up -d

models-init pulls only what the layers need, and /readyz shows the active layers ("layers":["l1","l2"]). What each layer detects and how they are fused: README, Models and Benchmarks.

Measured resource use#

Source. Measured on 2026-11-06 by the maintainers on one machine: an Apple M3 Max (arm64) MacBook Pro, Docker Desktop 28.4 with a Linux VM of 14 vCPUs and 15.4 GiB, images ghcr.io/guard-spec/guard-spec-gateway:0.1.0 (linux/arm64) and -control-plane:0.1.0, models guardspec-classifier@v3b and multilingual-e5-small@614241f. Memory and CPU are docker stats (sampled about once a second during the run; CPU 100% = one core). Load is ApacheBench, 8 concurrent clients, POST /v1/chat/completions with a system message and a 350-character user prompt, the stub upstream (no UPSTREAM_LLM_URL), so the numbers are the guard's own cost; every request also writes an audit row. Other hardware, x86-64 CPUs in particular, will differ: measure on yours (below) before you size a fleet.

Recommendations#

Starting points, from the tables above plus headroom. Only the "small team" row matches a measured configuration; the others are extrapolated from it. Requests/s are the guard alone; your upstream LLM's latency comes on top and does not use the gateway's CPU while it waits.

Setup Layers Host Gateway limit Roughly handles
Personal / laptop l1,l2 2 vCPU, 2 GB RAM free none tens of requests/s
Small team, one VM l1,l2 2 vCPU, 4 GB 2 CPUs, 1 GiB about 100 requests/s
Startup production, one VM l1,l2,l3 4 vCPU, 8 GB 2 to 3 CPUs, 2 GiB about 50 to 80 requests/s
More traffic l1,l2,l3 several gateway replicas (Kubernetes, Helm chart) 2 CPUs, 2 GiB each add replicas; throughput scales with cores
  • Memory: give the gateway at least 1.5 x its measured peak (light 768 MiB, full 1.5 GiB); the model weights are loaded once per process, whatever the concurrency.
  • CPU: throughput grows with cores up to INFERENCE_MAX_CONCURRENCY x INFERENCE_INTRA_OP_THREADS; set their product to the CPUs the gateway may use. More than that only adds contention.
  • DETECTOR_CASCADE=true skips L2 and L3 when L1 alone is decisive, which saves CPU on obvious traffic; it changes scores, so check it against your traffic first.
  • Rate limits (RATE_LIMIT_RPM) and an upstream timeout keep a burst from queueing up behind the model layers.
  • Kubernetes: the Helm chart's gateway defaults (500m CPU / 1Gi request, 2Gi memory limit) fit the full detector's measured peak; set INFERENCE_MAX_CONCURRENCY and INFERENCE_INTRA_OP_THREADS to the CPU limit as above (gateway.env), and scale with gateway.autoscaling (HPA). See values.yaml, the per-cloud examples in deploy/helm/guard-spec/examples/ and README, Kubernetes.

Long inputs#

A long text costs CPU in proportion to its length: the gateway cuts it into 2,048-byte chunks (untrusted text first into 24 KiB segments) and the classifier scores each chunk in 256-token windows. Today one request carries at most 128 KiB of untrusted text (about 30k tokens) and a single message at most 16 chunks; the numbers below say what larger documents would cost. How well the detector does on long text (false positives grow with length) is in benchmark, Long documents.

Measured with make bench-long (cmd/benchlong, the l1,l2 detector, one document at a time, K chunks of a document scored in parallel; 20k-token Wikipedia documents in English and Vietnamese). intra is INFERENCE_INTRA_OP_THREADS; "ORT default" lets ONNX Runtime use every core for each run.

  • The two runner rows are measured, but on different CPUs (GitHub assigns the host): the 2 vCPU job got a newer EPYC 9V74, the 4 vCPU job an EPYC 7763 that also ran the full corpus, so the 2 vCPU row is faster. Shared cloud vCPUs vary by 1.5 to 2 times between runs; read them as a range.
  • x86 cloud vCPUs are 3 to 4 times slower per core than an M3 Max here (about 780 tokens/s per vCPU at intra 1, K = 4, on the 4 vCPU runner against about 2,300 per M3 Max core).
  • The 8 and 16 vCPU rows are estimates, not measurements: they scale the 4 vCPU runner's rate per vCPU linearly, which assumes K and INFERENCE_MAX_CONCURRENCY grow with the cores. Replace them with your own run.
  • For a 10 s scanning budget this means roughly 30k to 50k tokens per request on 2 to 4 vCPU, 60k on 8 and 120k on 16 (estimated); 200k tokens in 10 s needs about 32 dedicated vCPUs or a GPU (an L4 takes about 3 s, see GPU below).
  • CPU per token barely changes with K or intra: more parallelism cuts the wall time of one document, not its cost. A server scanning documents for several users at once gets the same total throughput from intra 1 and many concurrent runs as from fewer, wider runs.
  • 100k and 200k-token documents, measured (Apple M3 Max, 2026-11-11, guardspec-classifier-v3b, commit 2b805cc; one Wikipedia document of each size per language from the long profile, scored alone with cmd/benchlong -docs, l1,l2). The cost is linear in the length: a 100k-token document takes 44.7 s (EN) / 39.8 s (VI) at intra 1 with one chunk at a time (2,200 to 2,500 tokens/s, 0.45 / 0.39 CPU-s per 1k tokens), 11.2 / 10.0 s with K = 4 (8,800 to 10,100 tokens/s), and 6.6 / 5.7 s with ONNX Runtime's default threads and K = 4 (15,300 to 17,900 tokens/s, 0.64 / 0.55 CPU-s per 1k tokens); a 200k-token document takes twice that (90.0 / 77.9 s, 22.7 / 19.6 s and 13.1 / 11.1 s). The classifier alone (l2, batched windows) scans 100k tokens in 32.8 s at intra 1 and 5.8 s with the default threads. Four long documents scored at once (the long profile's score pass, 128 documents, 18.0M tokens after the sanitizer) run at 7,100 to 7,900 tokens/s in total, 38 to 42 minutes for the whole profile. On a 4 vCPU cloud runner, 3 to 4 times slower per core, expect roughly 40 to 50 s per 100k tokens at best.
  • The gateway's long path costs less than the chunked numbers above. With MAX_SCAN_TOKENS set, a document past 128 KiB of untrusted text is tokenized once and scored in the classifier's 256-token windows, in batches, each window fused with L1 (ml.ScoreLong), not in 2,048-byte chunks. Measured as it runs with cmd/benchlong -long on (Apple M3 Max, 2026-11-11, guardspec-classifier-v6 with its cap and code corroboration, 4 documents at a time, ONNX Runtime's default threads): the long profile's 128 documents (18.0M tokens after the sanitizer) in 19 minutes, 15,600 tokens/s and 0.51 CPU-s per 1k tokens, against 7,100 tokens/s and 1.49 CPU-s per 1k tokens for the chunked measurement of the same documents (which runs the classifier twice, per window for l2 and per chunk for l1,l2); 256 documents of 100k to 200k tokens with an attack inside (31.9M tokens) at 17,900 tokens/s. So a 100k-token document costs about 50 CPU-seconds on this machine, about 26 s of wall time each when four are scored at once on its 14 cores (not measured alone).
  • The full per-run tables (L2 alone, every K, wall time per document) are in bench/results/long-m3max-local.md, long-gh-ubuntu-24.04-4vcpu.md and long-gh-ubuntu-24.04-2vcpu.md. The runner runs predate the 0.4.2 code/log fixes, so their false-positive tables show the 0.4.1 detector; latency is unaffected.

GPU option#

The CPU is the default; the GPU is an option (INFERENCE_PROVIDER=cuda, an image you build from build/gateway-gpu.Dockerfile, the FP16 classifier; deploy, GPU). Measured with bench/gpu/colab_gpu_bench.sh (cmd/benchlong, l1,l2, one document at a time) on Colab (shared VM), NVIDIA L4, driver 580.82.07, CUDA 12.9, ORT 1.31.1 gpu_cuda12, 12 vCPU Intel Xeon 2.2 GHz, 2026-11-12. Each figure is the median of 3 runs; a shared VM varies, read them as indicative. The documents are English Wikipedia texts of 20k, 100k and 200k tokens.

INFERENCE_BATCH_SIZE ms per window (L2) Tokens/s (L2) 20k doc, L2 100k doc, L2 200k doc, L2 200k doc, L1+L2
8 (default on CUDA) 1.21 156,000 0.12 s 0.64 s 1.29 s 3.1 s
32 1.71 111,000 0.18 s 0.90 s 1.81 s 3.1 s
64 1.79 106,000 0.19 s 0.92 s 1.91 s 3.1 s
128 1.90 100,000 0.19 s 0.97 s 2.05 s 3.1 s
  • "L2" is the classifier on every 256-token window of the document, as the long path runs it; "L1+L2" is the gateway's fused score per 2 KiB chunk. With the classifier on the GPU, L1 (the rules, on the CPU) takes most of the fused time: about 3.1 s for 200k tokens at every batch size, against 1.3 s for L2 alone. The 100k document takes 1.5 to 1.6 s and the 20k one 0.30 s with L1+L2.
  • Batch 8 was the fastest, so it is the CUDA default for the short and the long path (INFERENCE_BATCH_SIZE); larger batches were slower per window on the L4.
  • Against the CPU rows above, which were measured on CPU machines: a 200k-token document takes about 11 s on the M3 Max with every core (17,551 tokens/s), about 64 s on the 4 vCPU runner (3,106 tokens/s), and 41 to 47 s through the gateway's large-input lane with its default concurrency (PDF documents). The L4 takes about 3 s (L1+L2), so the 10 s budget fits about 640k tokens.
  • Parity, CUDA against the CPU on the same FP16 file and calibration (eval/data, and the bench/long quick dev documents: 2,176 rows, 2,456 chunks, 5,341 windows): the decisions at 0.85 are 100% identical and the mean absolute score difference is at most 7.1e-5; the largest difference is 7.6e-3 to 9.5e-3, because FP16 kernels differ between CUDA and the CPU. The parity criterion for FP16 is: decisions 100% identical, mean difference at most 1e-4, largest difference at most 1e-2 (1e-3 applies to FP32). The FP16 model itself differs from the INT8 CPU model on about 1% of decisions near the threshold (train/reports/fp16_agreement_v6.md).
  • The gateway on the same VM (PostgreSQL 17, the CUDA provider) reported "provider":"cuda" on /readyz and blocked an injection request.
  • T4 was not measured.

Measure long inputs on your hardware#

make bench-long                    # PROFILE=quick: about 1.6M tokens, about 7 minutes on an M3 Max
make bench-long PROFILE=full       # about 9.5M tokens
make bench-long PROFILE=long       # benign 100k and 200k documents only, 19M tokens, about 40 minutes per model on an M3 Max
# your own documents, no Python needed: one .txt file per document
go run -tags onnx ./cmd/benchlong -docs ./my-docs -lang en -host my-server

make bench-long needs uv for the corpus builder and downloads its pinned public sources once into bench/.cache. Both write bench/results/long-<host>.json and .md; the -docs form reports the score distribution, false positives and latency of your texts (it has no attacks, so no detection rate). Pin cores with taskset -c 0,1 and set INFERENCE_MAX_CONCURRENCY to match, as the 2 vCPU row does.

PDF documents#

A PDF sent inline is read by the gateway (PDF_EXTRACT, on by default) and its text is scanned like any long document, so a PDF costs the extraction plus the scan of its text at the rates above. Measured with BenchmarkPDFDocument (L1 only) and BenchmarkPDFDocumentML (the models behind ml.Live, as the gateway runs them; cmd/gateway/pdf_bench_test.go): a generated 100-page PDF with about 840 KB of benign text (207,629 tokens; 92 KiB of compressed PDF in base64) through the gateway to a fake upstream, on /v1/messages, chat completions and /v1/responses, with MAX_SCAN_TOKENS=250000 and INDIRECT_ACTION=redact so that every window is scored, no scan cache, one request at a time, 3 requests per API shape. Apple M3 Max (14 cores, 36 GB), macOS 15.4.1, Go 1.26, commit e637c60, 2026-11-11, local and indicative. Every number here is measured; nothing is estimated.

Step L1 only With the models (L1+L2 on 256-token windows, INFERENCE_INTRA_OP_THREADS=1)
Extract the text (PDFium in wazero) 0.65 to 1.1 s 0.95 to 1.2 s
Whole request (extract, sanitize, scan, forward) 0.93 to 1.6 s 41.5 to 47.2 s
Windows scored 479 chunks of 2 KiB, 0 skipped 1,093 windows, 0 skipped
Peak RSS growth over the 3 requests 0.2 MB 95 MB
Redacted (benign document taken for an injection) 0 of 3 0 of 3
  • The three API shapes give the same numbers within noise (with the models 41.5 s on /v1/responses, 45.8 s on /v1/messages, 47.2 s on chat completions; L1 only 1.52 to 1.61 s); the table shows /v1/messages.
  • Cold start: compiling the PDFium WebAssembly module took 1.5 to 2.4 s and the first document through a fresh runtime 0.66 to 1.1 s, with 50 to 150 MB of resident memory for the runtime. The gateway compiles the module in the background at start-up (/readyz does not wait for it), so a request pays it only when it arrives before the compile is done.
  • The scan dominates: extraction is 2 to 3% of the request with the models. The scan ran at about 4,500 tokens/s: the large-input lane's default of INFERENCE_LARGE_MAX_CONCURRENCY = CPUs / 4 (3 here) model runs at once, against K = 4 in the long-input table above; raise it to scan one document faster. On 2 to 4 cloud vCPUs expect 3 to 4 times longer per core, as that table says: a 200k-token PDF is minutes, not seconds, there.
  • Run-to-run spread on this laptop was large (extraction 0.65 s in one run and 1.1 s in another, the same code and document); read every figure as a range, as the ones above are written.
  • Memory: each document is parsed in a fresh PDFium instance whose linear memory (up to PDF_EXTRACT_MEMORY, 512 MiB) is returned afterwards; with a warm runtime the process grew by up to about 95 MB over the first three 200k-token requests and not at all over the later ones (the Go runtime keeps the memory). Count PDF_EXTRACT_MAX_CONCURRENCY × PDF_EXTRACT_MEMORY as the worst case on top of the figures in "Measured resource use".
  • A long benign PDF may still be blocked by the classifier (long-document false positives: the 1% target of RF-895d3533 was not met); run document-heavy applications with INDIRECT_ACTION=redact.

Reproduce (the second form needs the models and make onnx-deps):

go test ./cmd/gateway -run '^$' -bench 'PDFDocument$' -benchtime 3x
CGO_ENABLED=1 CGO_LDFLAGS=-L$PWD/.onnx/lib ONNXRUNTIME_LIB=$PWD/.onnx/lib/libonnxruntime.dylib \
  go test -tags onnx ./cmd/gateway -run '^$' -bench 'PDFDocumentML' -benchtime 3x

Disk#

  • Models: about 135 MB (light) or 270 MB (full) per version kept, plus older versions you pulled for rollback.
  • Images (unpacked, arm64): gateway 285 MB, control plane 46 MB, Postgres 415 MB, Caddy 88 MB.
  • Postgres: the audit table grows with every request. Measured on the stack above: 20,020 rows took 7.4 MB with indexes, about 380 bytes per request with the default AUDIT_STORE_CONTENT=false (hashes and lengths only). 1 million requests a day kept for the default 90 days (AUDIT_RETENTION_DAYS) is about 34 GB. Storing content adds the size of every prompt and response.
  • Logs: the production compose keeps at most 50 MB per container.

Measure on your hardware#

# 1. a key (see the README quick start), then a body like your traffic
cat > body.json <<'EOF'
{"model":"m","messages":[{"role":"user","content":"<a prompt of typical length>"}]}
EOF
# 2. load, while watching the containers
ab -n 5000 -c 8 -p body.json -T application/json -H "x-api-key: $KEY" \
  http://localhost:8080/v1/chat/completions
docker stats    # in another terminal
# 3. audit table size per row
docker compose exec postgres psql -U ps -d guardspec -c \
  "SELECT count(*), pg_size_pretty(pg_total_relation_size('requests')) FROM requests"

Run it without UPSTREAM_LLM_URL (stub answers) to see the guard alone, and once per DETECTOR_LAYERS value you consider. Reports with other hardware are welcome in an issue.
