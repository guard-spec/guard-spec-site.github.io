Operations

Audit privacy#

Audit rows (requests) store scores, the decision, and a SHA-256 and the length of the request body and of a buffered upstream response. They store no prompt or response content unless content storage is enabled, either for every organization with AUDIT_STORE_CONTENT=true on the gateway, or for one organization with PATCH /v1/organizations/{id} and {"audit_store_content": true} (admin role). Streamed responses are not buffered, so their response columns stay empty. With CONTENT_KEK (or a Vault Transit key) the stored content is encrypted with a data key of its organization (Encryption).

Each request gets one audit row. action is allow, block, error (the upstream failed or the client left before it answered) or output_leak (the canary showed up in the answer).

Retried refusals. Some clients send a refused request again: Claude Code sends it six times within a fraction of a second, the bodies differing a little. A request refused before the upstream (block by the sanitizer, the detector, the indirect threshold or a policy) whose org, API key, detection layer, injection label, policy rule and the hash of the text that triggered the refusal (the classified user turn, or the tool result or document that scored highest; not the whole body) match a refusal within AUDIT_DEDUPE_WINDOW (default 10 s, sliding with each repeat, at most 5 minutes per row) is not written as a row of its own: the first refusal's row gets repeat_count, the number of refusals it stands for (null for one), and only that row sends a detection.blocked event. Allowed, routed and redacted requests, upstream errors and output guard blocks always get their own row; metrics still count every request. The state is in the gateway process: with several replicas, retries that land on another replica start a row there. Migration 019 adds the column; the admin UI's request log shows it as ×N.

Shadow mode and model reload#

Shadow mode. With SHADOW_L2_MODEL=guardspec-classifier@v2 (or SHADOW_L2_MODEL_DIR), the gateway loads a second classifier next to the active one. For each sampled request (SHADOW_SAMPLE), every text the detector scores is scored again by the candidate, and its L2 verdict is fused with the same request's L1 and L3 scores and the candidate's own calibration and fusion weights. The request's comparison is the largest fused score of each side over its texts, and each side's decision at the direct threshold (0.85).

  • It runs asynchronously, never in the response path: the active result is returned at once and the candidate runs on its own goroutine and its own ONNX limiter (SHADOW_MAX_INFLIGHT), so it never takes a slot an active request waits for. When every slot is busy the text is not compared (skipped) rather than queued. The audit writer, already off the response path, waits up to SHADOW_TIMEOUT for it; a slower candidate is recorded as timeout. The cost is CPU: a candidate roughly doubles L2 work for sampled traffic, so lower SHADOW_SAMPLE on a busy gateway.
  • It never changes a decision, a response or a policy input.
  • Results go to shadow_results (migration 017), one row per compared request, written in the audit row's transaction and row-level secured per org like requests. A row holds the two model names, scores and decisions and a status (ok, timeout, error, skipped), never content, whatever the audit privacy settings. Rows are deleted with their request (audit retention).
  • Policies, sanitizer blocks and the indirect threshold are not replayed: the comparison is of the model layers.

Compare in the admin UI (Models), or with the API: GET /v1/organizations/:orgId/shadow?window=24h|7d|30d (viewer: agreement rate, shadow_would_block / shadow_would_allow, statuses, score means, p50/p95, the shadow − active delta and a 10-bin histogram) and GET /v1/organizations/:orgId/shadow/disagreements?direction=would_block|would_allow (admin: the disagreeing requests, newest first, paged; no content).

Reloading models without a restart. Two triggers, both on the gateway:

  • kill -HUP <gateway pid> (docker compose kill -s HUP gateway) reloads the current targets from disk: the pinned version, the manifest's recommended one when none is pinned, and the shadow candidate.
  • POST /admin/models/reload with Authorization: Bearer $GATEWAY_ADMIN_TOKEN reloads and can switch targets: {"l2_model":"guardspec-classifier@v2"}, {"l2_model_dir":"/models/x"}, {"shadow_l2_model":"guardspec-classifier@v3b"} or {"shadow_l2_model":"off"}. It answers 200 with the new generation, or 409 with the error. GET /admin/models returns the status. The routes do not exist unless the token is set; they are on the API port, so keep the token secret and the port off the Internet as usual.

A reload resolves the target, checks every file against the manifest's SHA-256 (the built-in manifest, or MODELS_MANIFEST; a directory that is not an install of a listed version is refused), loads the classifier fully and scores a warm-up text, and only then swaps it in atomically, with its own calibration and fusion weights. Requests in flight finish on the model they started with, which is closed once the last of them is done; none is dropped or fails. On any error the running models stay, the error is logged and /readyz reports it (detector.models.reload.error). A change made by the endpoint lasts until the next restart; pin it in .env (L2_MODEL) to keep it. With several gateway replicas, reload each one.

/readyz reports under detector.models: the running classifier as name@version and whether its files matched the manifest (l2_verified), the manifest's recommended version and whether it is installed, the versions installed in the cache, update_available, the shadow candidate and the last reload. The Models page shows it through the control plane (GATEWAY_URL, read server side); nothing calls the Internet. A new version shows up when a new manifest recommends it (a new image, or MODELS_MANIFEST); pull it (models pull), then reload.

Upstream behaviour#

UPSTREAM_LLM_TIMEOUT (default 5m) is the longest wait for the first byte and for any later silence; a long stream is not cut off while data flows. If the client hangs up before the upstream answers, the upstream request is cancelled at once. A client that only half-closes its side (shutdown(SHUT_WR)) sends the same FIN as one that left, and the gateway cannot tell them apart without writing to the connection, so by default it cancels too. Set CLIENT_HALF_CLOSE=wait to serve such clients: the gateway then cancels only on a connection reset and otherwise relies on the timeout.

Output guard#

The gateway checks the model's answer before the client sees it. It rewrites choices[].message.content (and choices[].text for legacy completions) in whole responses. In streams it holds back, per choice, the end of the text that could still turn into something to redact: an unfinished word, number, URL or reference definition, the start of the canary, an image, link or HTML tag that has not closed. So a pattern split across chunks is still caught, and nothing of it is sent before the guard has decided on it. It scans again every 64 new characters and rebuilds each chunk with its id, model and other fields unchanged. A stream therefore runs a little behind the upstream: usually under 64 characters plus the word being written, longer while an image, link or run of digits is still open (a word is held for at most 256 characters, an open construct or a run of digits for at most 8,192). Held text is flushed at finish_reason and at [DONE]. An upstream body that is not JSON cannot be checked and gives 502.

  • Images and links. Markdown images, HTML <img> tags and reference definitions whose host is not on the allowlist are removed ([REDACTED:image]). Links to other hosts keep their text and lose the URL. Bare image URLs that carry a query string are replaced with [REDACTED:url]; a bare URL runs, as GitHub's markdown reads it, to the next blank or <, brackets, parentheses and quotes included, and is checked from every place one starts. With the default empty allowlist every image and link is removed. An <img> tag is kept only if every src and srcset URL is on the allowlist.
  • HTML. For chat interfaces that render raw HTML, start tags that carry a URL a browser follows or loads are checked against the same allowlist (only http and https URLs can match, so javascript: and data: never do). A tag that needs a click (<a href> and ping, <area href>, <form action>, formaction) is removed alone, as a markdown link is: the text up to </a> stays and is checked like the rest. A tag that loads by itself is replaced with [REDACTED:image]: src or srcset of <img>, <source>, <video> (also poster), <audio>, <track>, <iframe> (any srcdoc), <embed>, <script>, <input>; <object data>, <link href>, <base href>, SVG <image>/<use> href, background, a style attribute with url() off the allowlist (or image-set(), @import, a backslash escape), any <style> element, a meta refresh, an SVG animation of href, and an event handler (onerror=). Tags are read as a browser reads them: attribute names in any case, quoted or not, line breaks inside the tag, > inside a quoted value, character references in URLs (&#x68;ttps:), and a tag inside another tag's attribute (which a browser reads as a tag when the other one is in a comment). A stream holds an open tag until its >, and removes one still open after 8,192 characters; a tag left open at the end of the answer is checked as it stands.
  • Personal data. Each match is replaced with [REDACTED:<type>]: email, phone (Vietnamese numbers in the +84, 84 and 0 forms, mobile and landline), cccd (12 digits starting with 0), card (13 to 19 digits that pass the Luhn check) and, when enabled, ipv4.
  • Canary. When enabled, the gateway puts a random token for each request in the system prompt (appended to a leading system message, or as a new one; legacy completions get none). If the model repeats it, the response is refused with 400 content_filter (in a stream, an error event that ends it), or the token is redacted. Either way the row's action is output_leak.
  • Values split by markup. Removing a link can join the text on either side of it: PS-CANARY-0123[]()4567… comes out as the whole token. The guard therefore looks for the canary and personal data again where a removal joined text, after rewriting, and in a stream holds back the text before a link that may be removed until it knows what follows. The joined value is redacted, or blocks the response, as if the markup had not been there.
  • Markup rebuilt by a removal. What is left around removed markup, or a marker next to (…), can form a new image, link, reference definition or URL: ![x][]()(https://evil.com/a.png) would become ![x](https://evil.com/a.png). The guard checks what it produced again with the same rules, up to three times, and removes what it finds as if it had been in the answer: here [REDACTED:image], and [REDACTED:email](https://…) keeps only its text, REDACTED:email. Markup nested deeper than that ends the answer with a marker. Streams hold back what a removal may still join and send what the whole answer would be.
  • Reasoning. The reasoning and reasoning_content fields that Ollama and vLLM send are guarded like the answer, or dropped.
  • Refusals and tool calls. refusal is guarded like the answer. Tool-call arguments (tool_calls[].function.arguments, and the older function_call) are parsed as JSON and each string is guarded on its own, so they stay valid JSON. In a stream, each call's arguments are held whole and sent when its choice finishes. A canary in tool-call arguments refuses the response even in redact mode.
  • Content parts. Text parts are guarded. A part that is not text cannot be checked: a whole response gets 502, and a stream ends with an error event.
  • Messages API blocks. On /v1/messages, text, thinking, tool and server tool input, citations (quoted text, title, URL) and the readable text of web search and web fetch results are guarded; encrypted content, ids, dates and signatures pass unchanged. redacted_thinking passes. A block of any other type is refused like a non-text part, or passed unchecked with OUTPUT_UNKNOWN_BLOCKS=pass.
  • Responses API items. On /v1/responses, output text, refusals, reasoning summaries and text, function-call arguments, custom tool input, web search queries and annotation URLs, titles and file names are guarded; encrypted reasoning and ids pass unchanged. When the guard changes a text, that text's annotations with offsets and its log probabilities are dropped, since they no longer match it. In a stream, the deltas, the .done events, output_item.done and response.completed all carry the same guarded text, and tool-call arguments arrive as one guarded delta before their .done event. Other output item types, content parts and stream events with content follow OUTPUT_UNKNOWN_BLOCKS.

The audit row counts what was removed per type in pii_entities, as output:email=2 (and, with personal data in requests on, what the request held, as input:pii_email=1). It never stores the content. These settings apply to every organization; there are no per-org output settings yet.

Indirect injection and tool poisoning#

Text that reaches the model from a third party (tool results, retrieved documents, and the tool descriptions an MCP server supplies) is untrusted. The gateway scores it apart from the user's own text.

Part Name in SCAN_ROLES Default Notes
user messages, legacy prompt and suffix user on classified together
tool (and function) messages tool on each message classified on its own
tools[].function.description and every description in parameters (also legacy functions[]) tool_descriptions on detector plus the MCP poisoning signals
system messages system off classified with the user text, never rewritten
assistant tool_calls[].function.arguments from history tool_calls off the string values of the JSON arguments, never rewritten

User and tool text is sanitized whether or not it is classified. A key that differs from tools or functions only in case is refused with 400. While tool_descriptions is on, so is a tools field that is not a list, a name or description that is not a string, and a schema nested deeper than 32 levels.

Scoring. Each tool result and each tool definition gets its own score. An instruction found in a tool result is indirect_injection; anything flagged in a tool description is tool_poisoning. A tool description's score is the larger of the detector's and the MCP signals': a secret path (~/.ssh, id_rsa, /etc/shadow), <IMPORTANT>, "do not mention this to the user", "send all emails to" or invisible characters reach 0.9 on their own; weaker signals ("Before using this tool", mcp.json, a description over 1500 bytes, ...) count 0.5 each and only block together. The request is blocked when the largest untrusted score reaches INDIRECT_BLOCK_THRESHOLD; with INDIRECT_ACTION=redact an offending tool result or document is replaced with a placeholder instead and the request goes on (tool descriptions still block). The audit row's injection_score and injection_label hold the strongest finding, direct or not. Untrusted text is limited to 128 KiB per request (413 above); a text longer than one detector call (about 28 KB) is scored in overlapping segments, every byte of it. On /v1/messages the limit counts what is actually classified: results found in the scan cache are not, and earlier turns missing from it have a budget of 1 MiB of their own. With MAX_SCAN_TOKENS set, a request past these limits is scanned on the long path instead of refused (Large inputs).

Spotlighting applies to tool results only:

SPOTLIGHT Effect on tool results
off (default) forwarded as sanitized, without markers
delimit wrapped in <<untrusted-XXXX>> ... <</untrusted-XXXX>> with a random boundary per request, and a note in the system message telling the model that text inside is data
datamark every space and tab replaced by ˆ (U+02C6), with a system note explaining the marker

The sanitizer strips spoofed markers from client text and raises the anomaly score when it finds one, so a tool result cannot close the block it sits in. An org can override scan_roles, spotlight and indirect_action through PUT /v1/organizations/:orgId/guard-settings, and lower the block thresholds of proxied requests with injection_threshold (the fused score of the scanned text, 0.85 by default) and indirect_threshold (tool results, documents and tool descriptions, INDIRECT_BLOCK_THRESHOLD). A threshold is a number in (0, 0.85]; the gateway uses the smaller of the org's value and its own, so an org can only make it stricter. unscanned_parts (allow, log or block) works the same way: the stricter of the org's value and UNSCANNED_PARTS applies (see Content the gateway cannot read). max_scan_tokens (1 to 10,000,000) caps the tokens scanned per request for the org: the smaller of it and MAX_SCAN_TOKENS applies, and with MAX_SCAN_TOKENS unset it only lowers today's limits; it never opens the long path (Large inputs). The gateway reads these settings on every request and fails closed with 503 if it cannot.

POST /guardrail/scan takes text, documents (at most 64, 128 KiB in total; source is web, email, file, tool or other), or both. The response has injection_score, injection_label, anomaly_score, had_tag_chars, had_bidi, bytes_removed, sanitized_text, blocked, verdict and a documents[] entry per document with its own score, category, detector_category, rules, blocked and verdict. A document is blocked at INDIRECT_BLOCK_THRESHOLD or when its anomaly score reaches 0.6. (toxicity_score is still in the response for compatibility and is always 0.)

POST /guardrail/scan/tools checks each tool's description and every description nested in inputSchema (at most 256 tools). Each tool gets score, category, signals, blocked, verdict and fields (the descriptions that scored at least 0.3 or carried a signal, by path).

go run ./cmd/eval -path tool scores the eval set through this untrusted-content path.

Conversation window#

Each request is scored as it is: with SCAN_HISTORY=latest (the default on /v1/messages and /v1/responses) only the trailing turn's user text is classified, so an instruction split over several user messages ("Remember: ignore all" / "previous instructions" / "and do it.") keeps every part under the block threshold. The conversation window scores the most recent user turns again, joined:

  • Window. The user text of each message (its text parts joined; on /v1/responses, each user input message) is one turn; a message or item that holds only tool results or tool outputs is not a turn. The last CONVERSATION_WINDOW_TURNS turns (default 4) are joined with a space, at most CONVERSATION_WINDOW_BYTES (default 8192) in all. Each turn gets an equal share of the bytes; a longer turn keeps its head and its tail, where the pieces of a split instruction meet, so padding one turn does not push the others out. A request with fewer than two user turns has no window.
  • Decision. The window is scored by the same detector (L1, and L2/L3 when loaded). The injection decision takes the larger of the window's score and the per-turn one, against the same threshold (0.85, or the org's lower injection_threshold).
  • Cache. On /v1/messages and /v1/responses the window's score goes through the scan cache (kind window), keyed on the SHA-256 of the joined text, and with SCAN_CACHE_BACKEND=redis or postgres through the shared layer too, so another replica reads it: an agent loop that resends the same user turns with new tool results reads it from the cache, and only a new user turn runs the detector on a new window. Earlier turns are never scored on their own again. Chat completions already classify all their user turns as one text; when that text is the window (only user text classified, no more turns than the window holds) its score is reused, with no second detector run.
  • Policies and audit. conversation.score is the window's score for policies (0 without a window). When the window scores higher than the per-turn text, injection.source_role is conversation and the audit row's injection_label and injection_score are the window's; a request it blocks gets the tag input:signal=conversation, and its detection event signal: conversation with the layer (l1, l2, l3) that scored highest.
  • Settings. CONVERSATION_WINDOW_TURNS=0 (or CONVERSATION_WINDOW_BYTES=0) turns it off. An org can turn it on or off and set both sizes in guard settings (conversation_window, conversation_window_turns, conversation_window_bytes; admin UI: Guard settings → Conversation window). On, for an org, uses the default size when the gateway has it off.

Test set. cmd/gateway/testdata/multiturn.json holds 24 multi-turn attacks (12 English, 12 Vietnamese: split overrides, role changes, prompt extraction, filter bypass) and 12 benign conversations (tutoring, bank support, coding help, travel, cooking and IT support, in both languages), written for this feature, not taken from eval/ or train/. Each attack turn on its own scores under the threshold with L1.

/v1/messages or /v1/responses, SCAN_HISTORY=latest Attacks blocked Benign allowed
L1, window off 0 / 24 12 / 12
L1, window on 24 / 24 12 / 12
L1+L2+L3, window off 6 / 24 12 / 12
L1+L2+L3, window on 22 / 24 12 / 12

The L1 rows hold for /v1/responses too (tested); the L1+L2+L3 rows were measured on /v1/messages. On chat completions and with SCAN_HISTORY=full, where the user turns are already classified together, L1 blocks all 24 with or without the window. With L1+L2+L3 two attacks pass even with the window: their joined text scores 0.97 with L1 but under 0.05 with the L2 classifier, and the fused score stays under the threshold (the same text sent as one message passes too). eval/ is single-turn, so the window does not change its numbers (L1: FPR 0.1 %, L1+L2+L3: FPR 1.4 % at the gateway decision, as before).

Latency. One more detector run per request that has a new window, and a cache lookup otherwise (BenchmarkConversationWindow, see Go benchmarks).

Personal data in requests#

An organization can have the gateway count the personal data in each request and give the result to its policy rules (ADR 0003). It is off by default; turn it on with input_pii: true in the org's guard settings (PUT /v1/organizations/:orgId/guard-settings, or admin UI: Guard settings → Detect personal data in requests). The setting is read per request, so a change applies to the next one. No migration is needed: guard settings are a JSON column.

  • What is found. The output guard's own detectors (outputguard.CountPII, shared code): email; phone, Vietnamese numbers in +84, 84 or 0 form with optional spaces, dots or dashes; card, 13 to 19 digits that pass the Luhn check; cccd, 12 digits starting with 0; ipv4. These are pattern checks, not full personal-data detection: names, street addresses, bank account numbers and other countries' phone and ID numbers are not found. A version such as 1.2.3.4 counts as ipv4, and a long order number can pass the Luhn check; test the kinds you care about ("card" in input.pii.kinds) rather than only the count when that matters.
  • Which text. The cleaned text the injection scan collects: user turns (every part, the legacy prompt and suffix, Responses prompt variables), tool results (also web search and fetch results and Responses tool output items) and documents (Messages API document and search_result blocks), on /v1/chat/completions, /v1/completions, /v1/messages and /v1/responses, streamed or not (/v1/embeddings and /guardrail/scan do not run the check). Earlier turns count too. System and developer prompts are not checked (nor Responses instructions), even when SCAN_ROLES scans them for injection: they are the application's own text and often hold example data, which would make every request match. Tool-call arguments in the history and tool descriptions are not checked either. A part that the org's scan roles leave out is not checked.
  • Rules. input.pii.kinds lists the kinds found (in the order above) and input.pii.count counts all values. Rules can log or block on them (or route, for example to a self-hosted model). The Simulator takes both fields (email, card and a number).
  • Keeping the data from the provider (input_pii_action, Guard settings → Before the request goes upstream). tokenize replaces each value with a token such as ⟦EMAIL_1⟧ (the same value, the same token) and puts the values back in the answer, streamed or not, before it reaches the client: the provider never sees them, the user does. redact replaces them with a label ([EMAIL]) for good. input_pii_kinds limits either to some kinds (default: all five). The replacement covers user turns, tool results and documents (after classification, so detection and rules see the request as sent) and the earlier answers the client sends back, assistant text and tool-call arguments included (a JSON number in the arguments is left alone). Left as they are: system and developer prompts, signed thinking blocks, the provider's own web search and fetch results. Tokens live only in memory for the request. A restored value passes the output guard like any other text, so OUTPUT_REDACT_PII=true shows the redaction in the answer. The audit row gets input:pii_tokenized_<kind>=<n> or input:pii_redacted_<kind>=<n>.
  • Audit and alerts. The audit row's pii_entities gets input:pii_<kind>=<n> tags; detection.blocked and detection.flagged events get pii_kinds and pii_count (alert conditions can use attrs.pii_kinds and attrs.pii_count). The values themselves are never stored, logged or sent.
  • Latency (Apple M3 Max, BenchmarkInputPII, a request whose text ends with an e-mail address and a phone number): the check adds about 11 µs to a 2 KB request (sanitize step 148 → 159 µs) and about 57 µs to a 20 KB one (1.62 → 1.68 ms); end to end with L1 the p50 goes from 1.18 to 1.20 ms (2 KB) and from 11.08 to 11.19 ms (20 KB). With the setting off nothing runs. See Go benchmarks.

Content the gateway cannot read#

The detector reads text. Images, files and audio in a request are forwarded to the model, which can read them (a vision model reads text in an image, a PDF's text reaches the model), so an injection inside a PDF or an image is not classified. UNSCANNED_PARTS makes these parts visible and lets you refuse them.

  • What counts. Chat completions: image_url, file (file_data or file_id) and input_audio content parts. /v1/messages: image blocks, and document blocks whose source is base64, url or file, also inside a tool_result. /v1/responses: input_image, input_file and input_audio. The kinds are image, file, audio and other: a part with no text of a type the gateway does not know, so a new provider part type is not missed.

  • Not counted, because they are scanned or are not input: text parts, document blocks with source text or content, search_result blocks, content the model produced in assistant turns, and encrypted reasoning and signatures.

  • Which turns. The same as the scan: on /v1/messages and /v1/responses with SCAN_HISTORY=latest the trailing turn only (full: every turn); on chat completions every turn, so an application that sends an image again with each request gets the tag on each request.

  • UNSCANNED_PARTS (gateway, default log):

    • log: forwarded; the audit row's pii_entities gets input:unscanned_image=<n>, input:unscanned_file=<n>, input:unscanned_audio=<n> and input:unscanned_other=<n> tags next to the PII tags (no migration).
    • block: the whole request is refused with HTTP 400 and nothing reaches the upstream. Chat completions and /v1/responses answer in the OpenAI shape with code unscanned_content; /v1/messages in the Anthropic shape (invalid_request_error). The message names the kinds found. The audit row records the block (detected unscanned, label unscanned_content).
    • allow: forwarded as before, counted in the metric only.

    Every mode counts the parts in guardspec_gateway_unscanned_parts_total{kind,action}.

  • Per organization. unscanned_parts in guard settings (PUT /v1/organizations/:orgId/guard-settings) can only make the gateway stricter (allow < log < block; the stricter value wins), like injection_threshold.

  • Rules. input.unscanned.kinds and input.unscanned.count are policy fields (the Simulator takes them too), so a rule can be narrower than the mode. For example, keep log for the org and refuse files only for the keys of one project (the keys a customer-facing app uses):

    curl -s $CP/organizations/$ORG/policies -H "$AUTH" -H 'Content-Type: application/json' -d '{
  "name": "no-files-public-app", "project_id": "<project id>",
  "rules": [{"name": "files", "action": "block",
    "condition": {"field": "input.unscanned.kinds", "operator": "contains", "value": "file"}}]}'

    request.tenant_id is the organization of the key, so an org-wide policy already applies to one tenant; use a project policy to single out some keys. A rule's block is a policy refusal (content_filter), not unscanned_content.

  • Not done here. The gateway does not extract the text of a PDF or run OCR. Have the application send the text instead of the file, or scan the extracted text at upload; see Files, PDFs and images.

Large inputs#

By default a proxied request may carry about 28 KB of user, system and tool-call text (16 chunks of about 2 KB), 128 KiB of tool results, documents and tool descriptions, and 1 MiB of earlier turns the scan cache does not have; past that it gets 413 and nothing goes upstream. Long documents (a contract, a log, a code base in the prompt) need more. MAX_SCAN_TOKENS raises the limit without scanning less:

  • Unset (the default): nothing changes. Same limits, same 413.
  • Set (for example MAX_SCAN_TOKENS=200000): it is the request's token cap, counted with the classifier's tokenizer (4 bytes a token without one); a request over it gets 413 before any scan and is never forwarded. A request within today's limits is scanned exactly as before: same chunks, same layers (L3 included), same scores. A request past them is large: it waits for the large-input lane, then its texts past one detector call are scanned on the long path, the rest as before.
  • The long path. Each long text is tokenized once and cut into the classifier's windows (256 tokens, overlapping by 64), so every token is scored; nothing is truncated or sampled. L1 runs on every window's text; windows with an L1 signal are scored first; windows of all the request's long texts share batches of 16; identical windows are scored once. Each window is fused from L1 and L2 with the classifier's L1+L2 weights (L3 is left out of the long path: on the public sets it did not help, at about 40% more cost); a text's score is its strongest window. When a window reaches the block threshold the request will be refused anyway, so the text's remaining windows are skipped (in INDIRECT_ACTION=redact mode tool results and documents are always scored in full). A model failure on the long path fails the request (503); it does not fall back to L1 alone.
  • The lane. INFERENCE_LARGE_MAX_CONCURRENCY large requests (a quarter of the CPUs by default, so the short path keeps the rest) are scanned at once, at most LARGE_SCAN_ORG_CONCURRENCY of one org; every model run of a large request takes a slot of the lane's own limiter, not of INFERENCE_MAX_CONCURRENCY. Others queue, first come first served, for LARGE_SCAN_QUEUE_TIMEOUT (30 s), then get 429 with Retry-After, in each API's error shape (OpenAI code scan_queue_full, Anthropic rate_limit_error); a full queue (8 per slot) answers 429 at once. Requests within today's limits never enter the lane, so they do not wait behind large ones.
  • Per organization. max_scan_tokens in guard settings lowers the cap for the org (see Indirect injection and tool poisoning).
  • Earlier turns missing from the scan cache may total max(1 MiB, 32 × MAX_SCAN_TOKENS) bytes and do not count toward the cap. Long-path verdicts are cached apart from segment verdicts; a verdict that stopped early is not cached.
  • Size. MAX_REQUEST_BYTES (4 MiB by default) bounds the body; 200k tokens of text is about 1 MB.

Before you raise it: the classifier was calibrated on short texts, and a long benign document has many windows, each a chance of a false positive. Expect long benign documents to be blocked more often than short ones. The classifier cap for untrusted content (l2_untrusted_max, set by the v5 candidate's calibration, in shadow mode for now) lowers this for tool results and documents; at most 1% on 100k–200k-token documents is not reached yet (task RF-895d3533). Try it on your own documents with AUDIT_STORE_CONTENT off and the request log's scores first. A 200k-token document takes tens of seconds to scan on a few cores (see docs/sizing.md). POST /guardrail/scan and /v1/embeddings keep today's limits.

Per-organization exemplars#

/v1/organizations/:orgId/exemplars stores {"label": "block"|"allow", "text": "...", "source": "..."} (at most 1,000 per org, 4,000 characters each). A block text counts as an attack for that org's requests (injection.category tenant_exemplar), and its calibrated L3 score is a floor for the fused score; an allow text lowers L3 only. The gateway embeds each org's exemplars once and reloads them when they change (checked at most every 5 s). They need the L3 model. Tenant exemplars live in the database only, never in this repository.

Tracing#

OpenTelemetry tracing is off unless OTEL_EXPORTER_OTLP_ENDPOINT (or OTEL_EXPORTER_OTLP_TRACES_ENDPOINT) is set. Spans go over OTLP/HTTP; gRPC is not supported. The gateway continues a W3C traceparent from the client and creates a server span per request with children sanitize, detect, policy, upstream, output_guard and output_guard.stream. OTEL_PROPAGATE_UPSTREAM=true sends traceparent to the upstream; it is off by default because it tells the upstream the trace ID.

Rate limits#

Each API key gets two token buckets: requests per minute and, optionally, tokens per minute (estimated as body bytes / 4). A key's own rpm_limit and tpm_limit win; keys without one get RATE_LIMIT_RPM / RATE_LIMIT_TPM. Over the limit: 429 with Retry-After and {"error":{"message":"...","type":"requests","code":"rate_limit_exceeded"}} (type is tokens for the token limit); no audit row. Buckets are kept in memory per gateway replica, and a key's limits are cached for 30 seconds.

POST  /v1/organizations/{id}/api-keys           {"alias":"bot","rpm_limit":600,"tpm_limit":200000}
PATCH /v1/organizations/{id}/api-keys/{prefix}  {"rpm_limit":null}   # back to RATE_LIMIT_RPM

Users, invites and projects#

Admins invite people with POST /v1/orgs/{id}/invites {"email":"a@example.com","role":"member","ttl_hours":72}. No e-mail is sent: the response carries a one-time gsinv_... token that the admin passes on, and POST /v1/invites/accept {"token":"...","password":"...","display_name":"A"} creates the user (or adds the membership to an existing account whose password matches). Only the token's SHA-256 is stored. Nobody can invite with a role above their own.

A project groups API keys inside an organization. A key or a policy created with a project_id belongs to that project; the gateway evaluates the project's policies first, then the org-wide ones.

Identity, SSO and two-factor authentication#

Sessions. A login creates a row in sessions; the token (12 hours) carries its id as sid. Logout, DELETE /v1/auth/sessions/:id, a password change (other sessions), disabling a user and an admin's revoke-sessions end sessions at once on the replica that made the change and within 15 seconds on the others. Tokens issued before migration 013 have no sid and are refused: everyone logs in again after the upgrade.

Two-factor authentication (TOTP, RFC 6238: SHA-1, 6 digits, 30 s, one step of skew). POST /v1/auth/mfa/totp/setup returns the secret and an otpauth:// URL (the UI draws the QR code itself); .../confirm {code} turns it on and returns 10 recovery codes, shown once and stored as bcrypt hashes. Enrollment is trust on first use: whoever completes it at the first login after an org requires 2FA (the account's password holder) chooses the authenticator. A login of a user with 2FA returns {"mfa_required": true, "mfa_token", "methods": ["totp","recovery"]}; POST /v1/auth/mfa/verify {mfa_token, code} finishes it. The mfa_token is a 5-minute JWT allowing 5 attempts and one success; a TOTP code is refused for the step it was used in (and earlier ones), a recovery code works once. Ten wrong codes in a row lock the user's second factor for 15 minutes (doubling every 5 more, at most 24 hours; 429 mfa_locked, logged as mfa.locked), whatever the token or address. The secret is encrypted with MFA_ENC_KEY (AES-256-GCM, bound to the user id). Back the key up with the database: without it no user with 2FA can log in.

A member's 2FA reset and session revocation act on the user everywhere, so they need an instance administrator or an owner of every organization the user belongs to (403 not_sole_authority otherwise).

Org security (PUT /v1/organizations/:orgId/security, owner): require_mfa makes members without 2FA enroll at their next login ({"mfa_enroll_required": true, "mfa_token"}; that token can only call the 2FA setup endpoints) and refuses existing sessions without 2FA (403 mfa_required); sso_satisfies_mfa lets SSO sessions pass; allowed_login_methods (password, google, oidc:<provider id>, saml:<provider id>; null allows all, and a body without the field keeps the stored value) refuses sessions of other methods (403 login_method_not_allowed); session_lifetime_hours (1-12) shortens sessions for this org; domain_join adds SSO users of a verified email domain on first login, with a role up to admin. A domain can be joined only if the instance administrator listed it in the provider's allowed_domains. scim_revoke_keys (default on) revokes the API keys a user created in the org when the org's SCIM client deactivates them.

SSO (OpenID Connect, Google as a preset). An instance administrator (users.is_instance_admin; the bootstrap admin, which is the earliest owner of the default org at migration 013) adds providers at /v1/admin/identity-providers {"type":"google","client_id":"...","client_secret_env":"OIDC_SECRET_GOOGLE","allowed_domains":["example.com"],"auto_provision":true}. Register <PUBLIC_BASE_URL>/v1/auth/oidc/<id>/callback as the redirect URI. The flow uses PKCE (S256), state and nonce (stored server-side for 10 minutes); the state is also bound to the browser by an HttpOnly, SameSite=Lax cookie set at start (login CSRF), so the UI navigates to .../start rather than fetching it. The callback verifies the ID token through the provider's JWKS and requires email_verified; Google logins with allowed_domains must also carry a matching hd claim. The callback redirects to /ui/#/auth/callback?code=<60 s one-time code> (or ?error=<code>), which POST /v1/auth/oidc/exchange turns into the same answer as a password login, so 2FA still applies. Identities match on (provider, subject). A new identity whose email matches an existing account links to it only when the provider has trust_email_for_linking (off by default) and the account has no password and no identity; otherwise the login is refused with account_exists, and the owner of the account links the identity from their profile: POST /v1/auth/identities/:providerId/link/start returns the provider's URL, the callback sends the browser to /ui/#/account?link_code=<60 s code>, and POST /v1/auth/identities/link/complete {code} with the same user's token binds it (a code is refused for anyone else, so a link URL sent to a victim links nothing). A manual link never runs domain_join. New users are created only with auto_provision and an allowed domain. Emails are stored lower-cased.

SAML 2.0. Guard Spec is a SAML service provider next to OIDC. An instance administrator adds a provider of type saml at /v1/admin/identity-providers with the identity provider's metadata instead of a client id and secret: {"type":"saml","display_name":"Okta","saml_metadata":"<md:EntityDescriptor ...>","allowed_domains":["example.com"],"auto_provision":true,"saml_groups_attribute":"groups"}. The metadata (at most 256 KiB; an EntityDescriptor, or the first one of an EntitiesDescriptor) must have an IDPSSODescriptor with a SingleSignOnService for the HTTP-Redirect binding and at least one signing certificate (a KeyDescriptor with use="signing" or no use); issuer is taken from its entityID, and client_id, client_secret_env and scopes are not used. allowed_domains, auto_provision, trust_email_for_linking and enabled work as for OIDC. The provider's answer (and the list) carries saml_sp, the values to enter at the identity provider, derived from PUBLIC_BASE_URL:

saml_sp field Value
entity_id (SP entity id, the audience) <PUBLIC_BASE_URL>/v1/auth/saml/<id>/metadata
acs_url (Assertion Consumer Service, HTTP-POST) <PUBLIC_BASE_URL>/v1/auth/saml/<id>/acs
metadata_url (SP metadata: AuthnRequestsSigned="false", WantAssertionsSigned="true", NameID formats persistent and emailAddress) <PUBLIC_BASE_URL>/v1/auth/saml/<id>/metadata
Provider field Default Meaning
saml_metadata required The IdP metadata XML: entity id, SSO URL, signing certificates. Paste it again when the IdP rotates its certificate
saml_allow_idp_initiated false Accept responses without InResponseTo (a login started from the IdP's dashboard). Such a response cannot be bound to a browser; see the security notes
saml_email_attribute empty Attribute holding the email. Empty: the first of email, mail, emailaddress, Email, http://schemas.xmlsoap.org/ws/2005/05/identity/claims/emailaddress, urn:oid:0.9.2342.19200300.100.1.3; then the NameID when it is an email
saml_name_attribute empty Attribute holding the display name. Empty: the first of displayName, name, http://schemas.microsoft.com/identity/claims/displayname, http://schemas.xmlsoap.org/ws/2005/05/identity/claims/name, urn:oid:2.16.840.1.113730.3.1.241, cn
saml_groups_attribute empty Attribute holding the groups (see group roles below). Empty: the first of groups, memberOf, http://schemas.microsoft.com/ws/2008/06/identity/claims/groups, Role, role the assertion has; at most 200 values of at most 256 characters

The login is SP-initiated: the UI navigates to GET /v1/auth/saml/<id>/start?redirect=/ui/..., which stores the AuthnRequest id for 10 minutes, binds it to the browser with an HttpOnly gs_saml cookie (SameSite=None and Secure when PUBLIC_BASE_URL is https://, Lax over http), and redirects to the IdP with an unsigned AuthnRequest (HTTP-Redirect, NameIDPolicy persistent). The IdP posts the response to the ACS, which accepts it only if:

  • the Response or the assertion is signed by a certificate of the metadata (only the signed element is read, which defeats XML signature wrapping) and the response holds exactly one assertion; encrypted assertions are not supported;
  • the status is Success, the issuer is the metadata's entity id, the Destination (when present) and the Recipient are the ACS URL, and an AudienceRestriction names the SP entity id;
  • the assertion's NotBefore (with 2 minutes of skew) and NotOnOrAfter hold, and the SubjectConfirmationData has not expired;
  • InResponseTo names a pending request of this provider started by this browser (the cookie); a response without it is accepted only with saml_allow_idp_initiated;
  • the assertion id was not used before (saml_assertions keeps it until the assertion expires).

The NameID (at most 255 characters) is the subject: identities match on (provider, NameID), so the IdP must send a stable one. Without an email the login is refused with email_not_verified. From there it is the OIDC flow: the same linking and provisioning rules, domain_join, the one-time code and POST /v1/auth/oidc/exchange, so 2FA and the org's rules still apply. The session's login method is saml:<provider id>, which allowed_login_methods accepts and sso_satisfies_mfa counts as SSO. An account with a password links a SAML identity from its profile as with OIDC: link/start returns the IdP's URL, the ACS sends the browser to /ui/account?link_code=<code> (or ?link_error=<code>), and link/complete with the same user's token binds it. Single logout is not supported. A refused login redirects to /ui/#/auth/callback?error=<code> (codes in docs/sso.md), and the control plane logs the reason (saml login refused).

SCIM 2.0 provisioning (RFC 7643, RFC 7644). An organization's identity provider creates, updates, deactivates and deletes the org's users and groups at <PUBLIC_BASE_URL>/v1/scim/v2, the same base URL for every organization: the bearer token names the org. An owner creates a token with POST /v1/organizations/:orgId/scim/tokens {"name":"Okta","expires_at":null}; the answer carries token (gss_ and 43 characters) once, and only its SHA-256 and a 12-character prefix are stored. An org has at most 20 active tokens (409). GET .../scim/tokens (admin) lists them with last_used_at, the base_url and the number of SCIM users and groups; DELETE .../scim/tokens/:id (owner) revokes one at once. A missing, revoked or expired token gets 401. Errors are SCIM errors ({"schemas":[...Error],"status","scimType","detail"}).

SCIM endpoint (under /v1/scim/v2) Notes
GET /ServiceProviderConfig, GET /ResourceTypes, GET /Schemas PATCH and filter supported; bulk, sort, ETag and password change not
GET /Users?filter=&startIndex=&count= filter on userName, externalId, id or emails.value; count 100 by default, at most 200
POST /Users; GET, PUT, PATCH, DELETE /Users/:id see below
GET /Groups?filter=&startIndex=&count=&excludedAttributes=members filter on displayName, externalId or id
POST /Groups; GET, PUT, PATCH, DELETE /Groups/:id members must be SCIM users of the org, at most 1000 per request

Filters are attribute eq "value" only (400 invalidFilter otherwise). Guard Spec keeps a user's userName, externalId, display name (displayName, else name.formatted, else name.givenName and name.familyName) and active; other attributes (the enterprise extension, phone numbers…) are accepted and ignored. The account email is userName when it is an email, else the primary (then the first) email. active may be a boolean or "True" / "False" (Entra ID). PATCH takes add and replace with a path (active, userName, externalId, displayName, name.formatted, any case) or without a path and an object value (Okta); remove is accepted and ignored. PUT changes only the attributes it carries. For groups, PATCH takes add, remove (without a value: all members) and replace on members, remove on members[value eq "<id>"] (Okta), replace on displayName or externalId, and an object value without a path (its members are added); it answers the group, or 204 when the request has attributes or excludedAttributes=members.

POST /Users creates an account without a password for a new email (the person signs in with SSO). An existing account is linked only if it is already a member of the org or the org claims its email domain with a domain_join rule; otherwise 409 uniqueness (invite it, or claim the domain), so an org cannot take over or lock out someone else's account. A userName is unique per org (409). A provisioned user joins with the member role (an existing member keeps theirs) until group mappings change it. Only for an account SCIM created does a new email userName change the account's email and a new display name change its name. A SCIM-created account has no password and no SSO identity, so its first SSO login links by email only when the provider has trust_email_for_linking; otherwise the login is refused with account_exists (see the setup guide).

Deactivation (active: false by PUT or PATCH):

  • removes the user's org and project memberships at once (the next request is refused) and keeps the role for a reactivation;
  • revokes the API keys the user created in the org, unless the org's scim_revoke_keys is off; keys created before migration 025 have no creator (api_keys.created_by) and are never revoked this way;
  • for an account the org owns (SCIM created it, or the org claims its domain with domain_join), revokes every session, and disables the account when it belongs to no other organization; other accounts keep their sessions and their other memberships;
  • is refused with 409 mutability for the org's only owner.

Reactivation (active: true) gives the membership back with the role the user's SCIM groups map to; when none matches, member if the org maps SCIM groups, else the role they had (an owner stays owner). It re-enables an account the deactivation disabled, unless an administrator disabled it again since. POST /Users with active: false for an existing member removes the membership as a deactivation does. DELETE /Users/:id deactivates an active user the same way, then removes the SCIM record: the account itself is not deleted (it stays disabled if the deactivation disabled it).

Group roles (GET /v1/organizations/:orgId/group-roles, admin; PUT replaces the whole list, owner): {"items":[{"provider_id":null,"group_key":"guardspec-admins","role":"admin"},{"provider_id":"<SAML provider id>","group_key":"guardspec-viewers","role":"viewer"}]}. At most 100 mappings; role is viewer, member or admin (never owner); group_key (1 to 256 characters) matches case-insensitively and is unique per provider.

  • provider_id null: the org's SCIM groups, matched by display name or external id. Once the org has such a mapping, an active SCIM user's role is the highest role mapped to their groups, or member when none matches; it is recomputed when their groups change, a group is renamed or deleted, and for every active SCIM user when the mappings are saved, and on reactivation. Without any SCIM mapping, roles are left alone. Changes are logged as member.role_from_group (source scim or saml).
  • provider_id a SAML provider: values of that provider's groups attribute. At every login through it, in each organization the user is already a member of (including one domain_join just added) that maps at least one group of this provider, the role becomes the highest mapped role the assertion lists, or member when none matches or the assertion has no groups. Organizations without a mapping for the provider are not touched, and a login never adds a membership.

In both cases an owner is never changed, and the IdP decides: a mapped role replaces the current one even when it is lower, and leaving the admins group takes the access away (at once with SCIM, at the next login with SAML). SAML role changes are logged as member.role_from_group.

Activity log. Member, invite, API key, policy, upstream, security and config changes and 2FA resets are recorded per org (GET /v1/organizations/:orgId/activity); SSO provider and instance user changes, logins (success and failure) and the user's own 2FA events at GET /v1/admin/activity. Details never hold secrets; a failed login keeps the email masked (a***@example.com). A refused SAML login is login.failed with method saml:<id> and the error code as reason. SCIM changes are in the org's log with the token as the actor (scim_token_id in the details): scim.user_created, scim.user_updated, scim.user_deactivated and scim.user_deleted (with keys_revoked and account_disabled; a deactivation also sessions_revoked), scim.user_reactivated, scim.group_created, scim.group_updated, scim.group_deleted; and so are scim.token_created, scim.token_revoked, scim.group_roles_updated and member.role_from_group (a SAML login changed a role; from, to, provider_id).

Bootstrap. ADMIN_EMAIL/ADMIN_PASSWORD create the first owner and instance administrator once. A later start does nothing if an instance administrator exists or the bootstrap ran before, so a deleted bootstrap admin stays deleted.

Audit retention#

The control plane deletes audit rows older than AUDIT_RETENTION_DAYS in batches, at start and then every AUDIT_RETENTION_INTERVAL. Every replica runs the job; a Postgres advisory lock lets one of them work at a time.

The same job, under the same lock and in batches of AUDIT_RETENTION_BATCH, deletes activity log rows older than ACTIVITY_LOG_RETENTION_DAYS (default 365) and sessions revoked or expired more than SESSION_RETENTION_DAYS (default 30) days ago. An active session is never deleted. 0 turns off either one. The activity log is row-level secured like the audit table, so its rows are deleted through a function with the table owner's rights (as for audit rows); the application role still cannot read or delete across orgs. Expired entries of the shared scan cache (SCAN_CACHE_BACKEND=postgres) go in the same run, whatever the retention periods are.

Scan cache#

Claude Code (/v1/messages) and Responses API clients (/v1/responses) resend the whole session every turn: system prompt or instructions, tool definitions and every earlier tool result. With SCAN_HISTORY=latest the gateway classifies each of those texts once and keeps its scores in a scan cache keyed by the org, the kind of text and the SHA-256 of its full content, for 6 hours. A request may classify at most 128 KiB of new untrusted text, plus 1 MiB of earlier turns that the cache does not have.

That cache is in each gateway process (SCAN_CACHE_SIZE). With more than one replica, a turn that lands on another replica, or any turn after a restart, finds the earlier tool results missing and classifies them again; past 1 MiB of tool output the session gets 413. SCAN_CACHE_BACKEND shares the cache:

Backend Where Notes
memory (default) each process as before
postgres scan_cache table (migration 020) of the gateway's database row-level secured by org like every tenant table; expired rows are never read and the control plane's retention job deletes them
redis SCAN_CACHE_REDIS_URL (Redis or Valkey; one endpoint, not Cluster) keys guardspec:scan:<sha256> with EXPIRE; compose has an optional scan-cache service (--profile scan-cache), the Helm chart reads the URL from a secret (gateway.scanCache)

The in-process cache stays the first layer: a request looks up every text it carries there, then the keys it lacks in the shared backend in one call, and writes what it scored to both in one call when it is done. Each call is bounded by SCAN_CACHE_TIMEOUT (50 ms). A backend that is down, slow or returns something unreadable only costs a scan: the content is classified as without the cache, and guardspec_gateway_scan_cache_errors_total counts it. Nothing is ever skipped because the cache is unavailable.

What is stored. Per text: the detector's scores (fused score, layer scores, category, rule ids, PII types and offsets) and the verdict of a tool result or tool definition, or the scores of a conversation window, plus the model identity they were computed with. Never the text, a tool name or anything else from the request; the key is a SHA-256.

Model identity. The shared key also covers the identity of the running detector: a SHA-256 of the gateway binary, of every file of the L2 classifier and L3 embedder, of the calibration in use and of the configuration that changes a score (DETECTOR_LAYERS, DETECTOR_FUSION, FUSION_L1_FLOOR, DETECTOR_CASCADE*). Replicas that run different models or versions, say during a rolling upgrade or a canary, never read each other's entries. A model reload (SIGHUP, /admin/models/reload) gives the new models a new identity and so new keys: nothing needs flushing, the old entries expire. Hashing the model files takes a moment after start or a reload; until it is done the shared layer is skipped. Per-org exemplars (L3) are not part of the identity: as with the in-process cache, a new exemplar applies to cached texts when their entry expires.

Security. Whoever can write to the shared backend can mark any content as clean for that org. Redis must be private (no public port, a network policy) and authenticated (requirepass or ACLs; rediss:// across networks); the compose service refuses to start without a password. Postgres uses the gateway's own role and row level security. See docs/security.

  • Migrations: migrations.enabled=true applies migrations/ (copied from the gateway image of the release) with golang-migrate in a pre-install / pre-upgrade hook, before dbRoles sets the application role password. It is off by default, as before: then migrate yourself first, as the owner role (migrate -path migrations -database "postgres://ps:...@host/guardspec" up). The services never migrate at startup.
  • Cloud and OpenShift examples: deploy/helm/guard-spec/examples/ has values for EKS, AKS, GKE and OpenShift (random UIDs, Routes). They are rendered and schema-checked in CI but not verified on those platforms.
  • Exposure and scaling: ingress (or route on OpenShift), gateway.autoscaling / controlPlane.autoscaling (HPA), *.podDisruptionBudget, *.topologySpreadConstraints, networkPolicy (API and metrics ports per source; optional egress restriction to DNS, the database and listed destinations) and serviceAccount (annotations for EKS IRSA, GKE or AKS Workload Identity; the API token is never mounted).
  • Shadow mode and model reload: gateway.shadow (off while model and modelDir are empty), gateway.modelsManifest (MODELS_MANIFEST) and gateway.adminToken.enabled (GATEWAY_ADMIN_TOKEN from existingSecret, off by default). The control plane gets GATEWAY_URL pointing at the gateway Service (controlPlane.gatewayURL; - leaves it unset), and with networkPolicy on, the chart lets it reach the gateway's port 8080. See Shadow mode and model reload. doctor reads the manifest of MODELS_MANIFEST too, unless -manifest is given.
  • Air-gapped or mirrored registries: docs/airgapped.md mirrors the images with their cosign signatures and attestations and the models, verifies them offline, points the chart at the mirrors and shows an External Secrets example.
  • doctor (/app/doctor in the gateway and control-plane images released from 0.2.0, and in the release archives) checks the database, the migration version, the model files against the manifest's SHA-256, which detection layers will load, the upstream, the security settings and whether a published security advisory affects the running version (-skip advisories without internet access). Exit code 0: nothing failed (warnings allowed); 1: a check failed (-strict: or warned); 2: usage error. -json for scripts.
  • Secrets come from existingSecret. GUARDSPEC_APP_PASSWORD reaches both services as PGPASSWORD, so URLs carry no password. POSTGRES_PASSWORD is used only by the optional migrations and dbRoles hook jobs. MFA_ENC_KEY (see Configuration) is optional in that Secret; it can come from controlPlane.extraEnvFrom instead.
  • Metrics are served on separate ClusterIP Services (*-metrics), so exposing an API Service never exposes /metrics. serviceMonitor.enabled=true adds a Prometheus Operator ServiceMonitor.
  • Models come from a PVC mounted read-only at /models in the gateway (models.existingClaim, or the chart's own with models.persistence.enabled=true, the default). The release gateway image is built with -tags onnx and runs L1 + L2 + L3 when the models are there; with an empty PVC it runs L1 only. With models.persistence.enabled=false and no existingClaim nothing is mounted at /models: use that with gateway.image.repository=ghcr.io/guard-spec/guard-spec-gateway-full, which has the models inside. models.pull.enabled=true adds an init container that runs ./models pull (Hugging Face, or models.pull.mirror) into the claim, or into a per-pod emptyDir without one, checking every file's SHA-256 against the manifest; a ReadWriteOnce claim serves one node only, so several replicas on several nodes need ReadWriteMany or the emptyDir. The readiness probe uses /readyz, which lists the active layers and answers 503 only when a layer the configuration requires (DETECTOR_REQUIRE_ML=true) is missing.
  • Resources: the gateway defaults (request 500m CPU / 1Gi, limit 2Gi) fit L1 + L2 + L3, which use about 900 MiB right after start.
  • Security: pods run as non-root with a read-only root filesystem, no capabilities and the RuntimeDefault seccomp profile. The dbRoles job runs as UID 70 (the postgres image's user) unless dbRoles.podSecurityContext sets one; on OpenShift it lets the SCC pick the UID.
  • Rate limits are per replica, so gateway.replicaCount (or the autoscaler) multiplies the effective limit.
  • Tested by the kind-e2e CI job (tests/kind/e2e.sh): images built from the change, an in-cluster Postgres and fake upstream, the migrations and dbRoles hooks, network policies, and EN / VI injections blocked with L1 only.
