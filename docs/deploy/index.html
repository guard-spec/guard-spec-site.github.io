Deploy

Tiếng Việt: README.vi.md.

Reference guides for running Guard Spec outside a laptop.

Status: reference templates, not yet verified by the maintainers. Community-tested: not yet. If you deploy this, please open an issue or a pull request with what worked and what did not. See CONTRIBUTING.md.

Guide Covers Status
aws.md EKS with the Helm chart, or ECS on Fargate; RDS for PostgreSQL 17, Secrets Manager, ALB + ACM, CloudWatch Template, not tested on AWS
gcp.md GKE Autopilot with the Helm chart, or Cloud Run; Cloud SQL for PostgreSQL 17, Secret Manager, HTTPS load balancer, Cloud Logging Template, not tested on GCP
on-premise.md One VM with Docker Compose, vanilla Kubernetes and OpenShift, air-gapped installs, a reverse proxy for TLS Template; the compose path is the one the README documents

What the maintainers did check while writing these guides, on a local Docker host with the 0.1.0 images: the migrations apply to PostgreSQL 17 with migrate/migrate:v4.20.1, deploy/postgres/set-app-password.sh sets the application role password, and guard-spec-gateway-full:0.1.0 and guard-spec-control-plane:0.1.0 start with an arbitrary non-root UID (group 0) and a read-only root filesystem, with /readyz reporting "layers":["l1","l2","l3"]. Nothing cloud-specific was run.

Read first#

These guides do not repeat the README. They assume you know:

  • Quick start and Production: the secrets and how the services refuse weak ones.
  • Install from a release: the images and archives.
  • Models and docs/models.md: models pull, pinning, rollback, air-gapped installs.
  • Configuration: every environment variable.
  • Operations, in particular Kubernetes and Identity, SSO and two-factor authentication.
  • Security model and limitations.

What every deployment needs#

Piece Notes
PostgreSQL 17 is what compose and CI use. Two roles: an owner role that runs the migrations (ps in compose) and guardspec_app, which migration 004 creates without a password. Roles are cluster-wide, so 004 fails on a server where guardspec_app already exists (another database or installation): give each installation a server of its own
Migrations migrations/ of the release tag, applied with migrate as the owner role, before the services start. The services never run them; the Helm chart does when migrations.enabled=true (a pre-install / pre-upgrade hook), otherwise you do
App password GUARDSPEC_APP_PASSWORD applied to guardspec_app after every migration run: deploy/postgres/set-app-password.sh or the chart's dbRoles job
Gateway ghcr.io/guard-spec/guard-spec-gateway:0.8.0 (models mounted at /models) or -gateway-full:0.8.0 (models inside). Port 8080 for clients, 9090 for metrics
Control plane ghcr.io/guard-spec/guard-spec-control-plane:0.8.0. Port 8081 for the API and the admin UI at /ui/, 9091 for metrics
Secrets GUARDSPEC_APP_PASSWORD (both services, as PGPASSWORD), JWT_SECRET, MFA_ENC_KEY and ADMIN_PASSWORD (control plane), the owner password (migrations only), UPSTREAM_LLM_KEY / UPSTREAM_KEY_* (gateway)
TLS The services speak plain HTTP. Terminate TLS in a load balancer or reverse proxy in front of them

Things that hold everywhere#

  • MFA_ENC_KEY must be backed up with the database. It encrypts every user's TOTP secret. Restoring a database without the key that matches it locks out everyone who has 2FA, and the control plane refuses to start without it once users have 2FA.
  • Keep the control plane private. Only the gateway's port 8080 needs to reach your applications. The control plane (API and admin UI) and both metrics ports belong on an internal network, a VPN or behind an identity-aware proxy.
  • /readyz answers 503 only for a missing required layer. With DETECTOR_REQUIRE_ML=true (set in gateway-full) a missing model layer stops the gateway at start (or, under GUARD_ENV=dev, makes /readyz answer 503). Without it, a gateway without its models runs L1 only and reports ready with "degraded":true. Check detector.layers and detector.degraded in a smoke test.
  • Rate limits are per gateway replica and in memory. Put a rate limiter or WAF in front for abuse protection.
  • Streaming. UPSTREAM_LLM_TIMEOUT defaults to 5m of silence. Load balancer idle or response timeouts shorter than your longest model answer cut streams; raise them.
  • Schema changes before 1.0. Read the CHANGELOG and snapshot the database before every upgrade.

The Helm chart on main#

Chart 0.4.0 (see Unreleased in the CHANGELOG) adds, each off by default: a migration hook (migrations.enabled), a model pull init container (models.pull, into the claim or a per-pod emptyDir, so several replicas no longer need a ReadWriteMany volume), Ingress and OpenShift Routes, HPA, PodDisruptionBudget, topologySpreadConstraints, NetworkPolicies and a ServiceAccount with annotations for IRSA and Workload Identity. Reference values per platform are in deploy/helm/guard-spec/examples/ (EKS, AKS, GKE, OpenShift): rendered and schema-checked in CI, installed on kind by the kind-e2e job with its own values, not verified on the clouds. Where a guide below shows plain manifests for one of these, the chart's values now do the same job.

Mirrored registries and disconnected clusters: ../airgapped.md (images with cosign signatures and attestations, models, offline verification, chart values, External Secrets). After installing, kubectl exec deploy/<release>-guard-spec-gateway -c gateway -- ./doctor (images from 0.2.0) checks the database, migrations, models, layers, upstream and security settings.

Since chart 0.1.1 (see the CHANGELOG): /models is mounted only with a models claim (or models.pull), so guard-spec-gateway-full works with models.persistence.enabled=false; the gateway defaults to a 2Gi memory limit; the dbRoles job takes its securityContext from values and leaves the UID to OpenShift; and MFA_ENC_KEY can sit in existingSecret.

Patching the chart output. Helm 4 accepts only post-renderer plugins for --post-renderer; a plain script, as Helm 3 allowed, is rejected (plugin ... not found). To add kustomize patches, wrap the script in a post-renderer plugin, or render and apply without a Helm release: write helm template output into a kustomization's resources, then kubectl kustomize <dir> | kubectl apply -f -. Hooks such as dbRoles then run as ordinary Jobs, not before the services.

GPU (optional)#

The CPU is the default: the published gateway image runs the INT8 classifier on ONNX Runtime's CPU provider and needs nothing else. Sizing gives the CPU numbers; for long documents (100k+ tokens) the CPU path needs many cores, and a GPU is the option.

The GPU path is supported in the code and measured (GPU rows in sizing), but no GPU image is published: build your own from build/gateway-gpu.Dockerfile (linux/amd64; the same gateway binary with ONNX Runtime's CUDA 12 build on NVIDIA's CUDA 12 + cuDNN 9 runtime image, about 5.7 GB unpacked) and push it to your registry:

docker build --platform linux/amd64 -f build/gateway-gpu.Dockerfile \
  -t <registry>/guard-spec-gateway:<version>-gpu .
docker push <registry>/guard-spec-gateway:<version>-gpu

By building and running it you accept NVIDIA's terms for the CUDA and cuDNN libraries of its base image (see NOTICE). CI builds this Dockerfile on every pull request, without pushing, to keep it working. It needs:

  • an NVIDIA GPU with driver 525 or newer;
  • the NVIDIA container runtime (docker run --gpus all ...), or on Kubernetes the NVIDIA device plugin or GPU Operator;
  • the FP16 classifier, model_fp16.onnx, next to the INT8 one: ./models pull -provider cuda (the models.pull init container does this when gateway.gpu.enabled). Without it CUDA runs the INT8 model, slowly, and doctor warns.

INFERENCE_PROVIDER picks the provider (the GPU image sets cuda):

Value Behaviour
cpu The default. CPU provider, INT8 model; nothing changes.
cuda CUDA execution provider on INFERENCE_CUDA_DEVICE_ID (default 0), FP16 model. If CUDA cannot start (no GPU, no driver, the CPU image) the gateway exits at start with an error that says what is missing, rather than running slowly on the CPU.
auto CUDA when it starts, else the CPU with a warning (and the reason in /readyz).

On CUDA, INFERENCE_BATCH_SIZE defaults to 8 windows per run (the short and the long path; the fastest on an L4) and INFERENCE_MAX_CONCURRENCY to 2; tune them with the GPU numbers in sizing. GET /readyz reports detector.inference (requested and active provider, GPU, driver, CUDA and ONNX Runtime versions, batch size, l2_model_file), and ./doctor checks the same before the gateway starts (inference).

With the Helm chart, name your image; the chart refuses gpu.enabled without it:

gateway:
  gpu:
    enabled: true     # your image, resources.limits["nvidia.com/gpu"]: 1, INFERENCE_PROVIDER=cuda
    # provider: auto  # fall back to the CPU instead of refusing to start
    image:
      repository: <registry>/guard-spec-gateway
      tag: <version>-gpu
  nodeSelector:
    nvidia.com/gpu.present: "true"
  tolerations:
    - {key: nvidia.com/gpu, operator: Exists, effect: NoSchedule}
models:
  pull:
    enabled: true     # also fetches model_fp16.onnx

The chart's ci/gpu-values.yaml is rendered and schema-checked in CI. In CI the image runs on a runner without a GPU, where it must refuse to start with cuda and fall back with auto; GPU numbers are measured separately and marked as such in sizing.

Contributing#

If you run Guard Spec on one of these platforms, a short report helps more than a polished guide: platform and versions, what you changed from the guide, and what failed. Open an issue or a pull request against docs/deploy/ (see CONTRIBUTING.md; commits need a DCO sign-off). Security problems go through SECURITY.md, never a public issue.
